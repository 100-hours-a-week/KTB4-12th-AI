## 1. 의존성 주입 (Dependency Injection)

**개념.** 함수나 클래스가 필요한 도우미(DB 접근, HTTP 클라이언트)를 **스스로 만들지 않고 인자로 받는** 것. 그러면 부르는 쪽이 진짜 대신 가짜를 줄 수 있고, 만드는 코드가 한 곳에 모인다.

**우리 코드.** 세 층에서 나온다.
- 업무 함수는 키워드 인자로 받는다 — [pipeline.py:138–141](../../src/profiling/pipeline.py) `profile(rq, *, catalog, store, recipient_store, pool_size)`.
- 라우터는 FastAPI 의 `Depends` 로 받는다 — [intake.py:283–292](../../src/profiling/intake.py):

```python
# intake.py:283-292 (발췌)
async def extract_and_pool(
    body: ProfileExtractRequest,
    catalog: Annotated[CatalogReader, Depends(get_catalog)],
    store: Annotated[ProfileRunStore, Depends(get_store)],
    ...
    supervisor: Annotated[Supervisor, Depends(get_supervisor)],
    settings: Annotated[Settings, Depends(settings_dep)],
    io_limiter: Annotated[anyio.CapacityLimiter, Depends(get_io_limiter)],
) -> SuccessResponse[ProfileAccepted]:
```
- `Depends(get_catalog)` 가 돌려주는 것은 `request.app.state.catalog` — 조립 뿌리 [main.py:51–85](../../src/profiling/main.py) 가 한 번 만들어 둔 객체다([02 §5](02_아키텍처.md)).

**왜 이렇게 했나.** `profile()` 이 안에서 `DbProfileRunStore(engine)` 을 만들면 단위 시험이 DB 를 찾는다. 인자로 받으니 [tests/unit/test_pipeline.py:165–172](../../tests/unit/test_pipeline.py) 가 가짜 셋을 넣어 0.01초에 시험한다.

**대안과 트레이드오프.** DI 컨테이너 라이브러리 — 자동이지만 "어디서 만들었지"가 마법이 된다. 모듈 전역 — 가장 짧지만 시험이 무거워진다. 지금 방식의 비용: 인자 목록이 길다(`extract_and_pool` 인자 8개).

**확인해 보기.** `grep -n "Depends(" src/profiling/intake.py` — 의존성 여덟 개가 전부 `async def` 함수를 가리킨다(이유는 [05 §2](05_동시성.md)).

## 3. 전략 (Strategy)

**개념.** 같은 일을 하는 구현이 둘 이상일 때, 부르는 쪽 코드를 바꾸지 않고 **설정으로 고른다**.

**우리 코드.** [main.py:62–63](../../src/profiling/main.py):

```python
app.state.catalog = (DbCatalogReader(app.state.engine, poll_ttl_s=settings.CATALOG_POLL_TTL_S) if settings.CATALOG_SOURCE == "db"
                     else FileCatalogReader(Path(settings.CATALOG_FILE)))
```

두 구현의 역할은 [catalog.py:1–7](../../src/profiling/catalog.py): DB 는 배포용(컨테이너에 파일이 없다), 파일은 로컬·시험용. 어느 쪽이든 `active()` 가 `(버전, 상품)` 을 준다.

**왜.** 로컬에서 4,231건 DB 를 매번 띄우지 않고 111건 JSON 으로 돌리려고. 시험도 파일 카탈로그로 돈다.

**대안.** 구현 하나만 두고 로컬에서도 DB — 단순하지만 시험이 느리다. **확인해 보기.** `PROFILING_CATALOG_SOURCE=file` 로 띄우면 기동 로그가 `FileCatalogReader 로드 catalog_sample.json: 상품 111건` 이다.

## 4. 널 오브젝트 — "없음"을 같은 모양으로 (대역)

**개념.** 어떤 것이 없을 때 `None` 을 두면 쓰는 곳마다 `if x is None` 이 필요하다. 대신 **같은 모양이지만 아무것도 안 하는(또는 항상 실패하는) 객체**를 두면 쓰는 코드가 단순해진다.

**우리 코드.** [main.py:121–129](../../src/profiling/main.py) `_NoCatalog`:

```python
class _NoCatalog:
    """카탈로그 로드에 실패했을 때 app.state.catalog 자리에 두는 대역 — active()가 항상 NoActiveCatalog.
    CatalogReader 모양(active)만 맞추면 되므로 상속 없음."""
    def __init__(self, reason: str) -> None:
        self.reason = reason
    def active(self):
        raise NoActiveCatalog(self.reason)
```

[main.py:67–69](../../src/profiling/main.py) 에서 카탈로그 로드가 실패하면 이 객체를 꽂는다. `by_id` 는 없다 — v1 에서 아무도 안 부르기 때문(`Protocol` 은 부르는 순간에만 검사한다).

**왜.** 카탈로그가 없어도 앱은 떠야 한다(`/health` 로 상태를 보이고, 7.6 은 503). `app.state.catalog` 를 `None` 으로 두면 `intake`·`/health` 둘 다 `None` 검사를 해야 한다.

**대안.** `Optional[CatalogReader]` + 검사 — 두 곳뿐이라 가능하지만, 자리가 늘면 빠뜨린다. **확인해 보기.** 활성 카탈로그를 비활성화하고([09 §… 부하 결과 재현](09_운영과_도구.md)) 앱을 띄우면 로그 `활성 카탈로그 없음 … 7.6은 503`, `/health` 의 `catalog.active: false`.

## 5. 리포지토리 (Repository)

**개념.** 표 하나(또는 한 묶음)에 대한 읽기·쓰기를 **클래스 하나**에 모아, 나머지 코드가 SQL 을 모르게 한다. 우리는 ORM 없이 **SQLAlchemy Core 의 `sa.text`** 로 SQL 을 그대로 쓴다.

**우리 코드.** [stores.py:148–274](../../src/profiling/stores.py) `DbProfileRunStore`(save·get·get_run·run_lock·recover_stale_runs·undelivered_count·delete_recipient), [stores.py:298–333](../../src/profiling/stores.py) `DbRecipientProfileStore`(upsert·get·delete). SQL 문장은 모듈 상수(`_RUN_UPSERT` 등)로 위에 모여 있고, 실행은 [stores.py:61–71](../../src/profiling/stores.py) `_one` 하나가 한다.

**왜.** SQL 이 한 파일에 모이면 표를 바꿀 때 볼 곳이 하나다. ORM 을 안 쓴 이유: 문장이 열 개 남짓이고 upsert 의 병합 규칙([07 §3](07_데이터와_DB.md))을 SQL 로 그대로 보는 편이 명확하다.

**대안.** ORM(SQLAlchemy ORM·SQLModel) — 표가 늘고 관계가 복잡해지면 유리. 지금은 자동 생성(autogenerate)도 포기했다([07 §8](07_데이터와_DB.md)). **확인해 보기.** `grep -n "sa.text" src/profiling/stores.py | wc -l` — SQL 이 이 파일 밖에 있는지 `grep -rn "sa.text" src/profiling/ | grep -v stores.py` 로 본다(카탈로그 읽기와 `alembic_version` 확인뿐).

## 6. DTO 와 부패 방지 매퍼

**개념.** 바깥 계약(HTTP 필드 이름, camelCase)이 바뀌어도 안쪽 코드가 흔들리지 않게, **바깥용 자료형(DTO)** 과 **안쪽 자료형**을 나누고 둘 사이 변환을 **정해진 곳**에서만 한다. DDD 에서는 이 변환층을 부패 방지 계층이라 부른다 — 바깥의 이름·구조가 안으로 "스며들지" 않게.

**우리 코드.** 바깥은 [schemas.py](../../src/profiling/schemas.py)(camelCase, 계약 1:1), 안은 [types.py](../../src/profiling/types.py)(snake_case). 변환 함수:

| 방향 | 함수 |
|---|---|
| 7.6 DTO → 내부 요청 | [pipeline.py:58–66](../../src/profiling/pipeline.py) `to_internal` |
| 내부 결과 → 7.7 DTO | [backend.py:38–51](../../src/profiling/backend.py) `callback_body` |
| 내부 결과 → 프로필 행 | [types.py:263–286](../../src/profiling/types.py) `from_outcome` |
| DB 행 → 내부 결과 | [stores.py:126–145](../../src/profiling/stores.py) `_to_outcome` |
| 원형 파일·DB 행 → 상품 DTO | [catalog.py:75–90, 301–307](../../src/profiling/catalog.py) |

```python
# pipeline.py:58-66
def to_internal(body: ProfileExtractRequest) -> ProfileRequest:
    return ProfileRequest(
        recipient_user_id=body.recipientUserId,
        source_version=body.sourceVersion,
```

**왜.** 계약 문서가 바뀌면 `schemas.py` 와 변환 두 곳만 바뀐다([schemas.py:3–4](../../src/profiling/schemas.py)). 이름 대조는 [이름_대조표](../../이름_대조표.md)에 있다.

**대안.** DTO 를 안에서 그대로 쓰기 — 파일이 줄지만 camelCase 가 SQL·로그·시험까지 퍼진다. **확인해 보기.** `grep -rn "recipientUserId" src/profiling/*.py | grep -v "schemas.py\|pipeline.py\|backend.py\|intake.py"` — 나오면 안 된다.

## 7. 관대한 읽기 / 엄격한 쓰기 (Tolerant Reader)

**개념.** 남이 보내는 것은 **너그럽게** 받고(모르는 필드 무시, 별칭 허용), 내가 보내는 것은 **엄격하게** 만든다(정해진 필드만). 연동 초기에 양쪽이 조금씩 어긋나도 서비스가 멈추지 않게 하는 원칙이다.

**우리 코드.** pydantic 의 `extra` 설정 세 가지가 그 표현이다.

| 대상 | 설정 | 어디 | 태도 |
|---|---|---|---|
| 7.6 요청(받는다) | `extra="allow"` + 모르는 필드는 **경고 로그** | [schemas.py:78–80, 113–123](../../src/profiling/schemas.py), [intake.py:310–313](../../src/profiling/intake.py) | 받되 기록한다 |
| 7.7 본문(보낸다) | `extra="forbid"` | [schemas.py:143](../../src/profiling/schemas.py) | 계약 밖 필드는 만들지도 못한다 |
| 7.9 상품(받는다) | `extra="ignore"` + 별칭(`views`·`view_count`·`available`) + boolean→3값 | [schemas.py:167, 182, 187, 191–197](../../src/profiling/schemas.py) | 버리지 않고 맞춰 읽는다 |

**왜.** Backend 가 필드를 하나 더 보냈다고 400 을 내면 연동이 깨진다. 반대로 우리가 보내는 본문에 실수로 태그가 섞이면(DR-035 위반) 계약 위반이라 `forbid` 로 원천 봉쇄.

**대안.** 전부 `forbid` — 계약을 엄격히 지키게 하지만 연동 중 잦은 400. **확인해 보기.** 7.6 에 `"foo": 1` 을 넣어 보내면 202 이고 로그에 `CONTRACT_7_6_UNKNOWN_FIELD … unknown={'': ['foo']}`.

## 8. 컨텍스트 매니저 — 자원의 시작과 끝을 `with` 로

**개념.** "열었으면 반드시 닫는다"를 `try/finally` 로 매번 쓰는 대신 `with` 한 줄로. 파이썬은 `@contextmanager` 로 함수 하나를 컨텍스트 매니저로 만든다 — `yield` 앞이 시작, 뒤가 끝(예외가 나도 실행).

**우리 코드.**
- [stores.py:188–234](../../src/profiling/stores.py) `run_lock` — 잠금 획득 → `yield got` → 해제·커넥션 반납. 쓰는 쪽은 `with store.run_lock(rid, sv) as got:` 한 줄([intake.py:261](../../src/profiling/intake.py)).
- [stores.py:50–58](../../src/profiling/stores.py) `_autocommit` — 커넥션 열고 닫기.
- [main.py:51–95](../../src/profiling/main.py) `lifespan` — `@asynccontextmanager`: `yield` 앞이 기동, 뒤가 종료. FastAPI 가 앱 수명에 맞춰 부른다.
- SQLAlchemy 의 `engine.begin()`([stores.py:68, 247](../../src/profiling/stores.py)) — 나가면서 COMMIT, 예외면 ROLLBACK.

**왜.** 잠금을 해제하지 못하면 그 키가 영영 막힌다. `finally` 를 호출자마다 쓰게 하면 언젠가 빠뜨린다.

**대안.** 명시적 `acquire()/release()` 메서드 — 잊기 쉽다. **확인해 보기.** [tests/unit/test_stores_lock_key.py](../../tests/unit/test_stores_lock_key.py) 의 "예외 뒤 thread-local 이 비워진다" 시험.

## 9. 명령 객체 + 워커 풀 (상한 큐 · 포이즌 필)

**개념.** "할 일"을 `(함수, 인자)` 값으로 만들어 큐에 넣으면, 누가 언제 실행할지를 넣는 쪽과 분리할 수 있다. 워커 풀은 그 큐를 비우는 스레드 묶음이다.

**우리 코드.** [supervisor.py:31](../../src/profiling/supervisor.py) `_Item = tuple[Callable, tuple, dict]`, 넣기 [104–117](../../src/profiling/supervisor.py), 꺼내 실행 [121–140](../../src/profiling/supervisor.py). 라우터는 `supervisor.submit(dispatch, rq, catalog, …)` 로 "무엇을 어떤 인자로" 만 넘긴다([intake.py:320–321](../../src/profiling/intake.py)). Supervisor 는 `dispatch` 가 무엇인지 모른다.

**왜.** [05 §4](05_동시성.md) — 대기가 큐에서 일어나야 스레드풀 토큰을 안 쓴다. 명령이 값이라 시험은 `FakeSupervisor` 가 기록만 하고 나중에 `run()` 으로 돌린다([tests/unit/test_intake_dedupe.py:118–133](../../tests/unit/test_intake_dedupe.py)).

**대안.** `threading.Thread(target=dispatch).start()` 를 요청마다 — 상한도 통계도 없다. **확인해 보기.** [05 §11](05_동시성.md).

## 10. 재시도 · 백오프

**개념.** 네트워크나 상대 서버의 **순간** 실패는 조금 기다렸다 다시 하면 대개 된다. 대기를 점점 늘리는 것이 지수 백오프. 다만 "다시 해도 같은 답"(4xx)에는 재시도가 무의미하고, 횟수 상한이 없으면 영원히 돈다.

**우리 코드.** [intake.py:160–187](../../src/profiling/intake.py) `_send_and_record` — 5xx·네트워크(=RESULT_READY)일 때만, `backoff_s × 4^(n-1)`(0.5초, 2초), 최대 `CALLBACK_MAX_ATTEMPTS`(3, 최초 포함). 어댑터 [backend.py:106–141](../../src/profiling/backend.py) 는 **한 번만** 보낸다 — 정책은 호출자에. 설정은 [settings.py:35–42](../../src/profiling/settings.py).

**왜.** 최악 대기(0.5 + 2 + 타임아웃 5초 × 3 ≈ 17.5초)를 계산 가능하게 두고, 그 뒤엔 Backend 의 재요청에 맡긴다([04 §7](04_통신.md)).

**대안.** `tenacity` 같은 데코레이터 — 짧지만 "언제 재시도하나"가 데코레이터 인자 속에 숨는다. 어댑터 안에서 재시도 — 어댑터가 `sleep` 을 하게 돼 시험이 느려진다. **확인해 보기.** [tests/unit/test_callback_retry.py:33–60](../../tests/unit/test_callback_retry.py) — `sleep=waits.append` 로 기다린 시간만 기록해 `[0.5, 2.0]` 을 확인한다.

## 11. 순수 판정 함수 — 멱등의 심장

**개념.** 입력만으로 출력이 정해지고 부작용(DB·시간·네트워크)이 없는 함수를 **순수 함수**라 한다. 결정을 순수 함수로 빼면 표 하나로 시험할 수 있고, 어디서 부르든 같은 답이다.

**우리 코드.** [intake.py:198–221](../../src/profiling/intake.py) `decide(existing, input_hash, *, stale_after_s, now=None) -> (행동, 이유)`. 시간도 인자로 받는다(`now`, [224–230](../../src/profiling/intake.py) `_age_s`). 부르는 곳은 잠금 안 [261–273](../../src/profiling/intake.py). 입력 정규화는 [pipeline.py:69–75](../../src/profiling/pipeline.py) `input_hash`.

**왜.** 판정 규칙 10가지를 DB 없이 표로 시험한다([tests/unit/test_intake_dedupe.py:54–68](../../tests/unit/test_intake_dedupe.py)) — 규칙이 바뀌면 표 한 줄이 바뀐다. "이유" 문자열을 같이 돌려주니 로그가 곧 설명이다.

**대안.** 잠금 안에서 `if` 를 직접 — 시험하려면 DB 와 잠금이 필요. **확인해 보기.** [04 §8](04_통신.md)의 코드 발췌를 표로 옮겨 보고 시험 파일의 10줄과 맞춰 본다.

## 12. 상태 기계 + DB 불변식

**개념.** [07 §9](07_데이터와_DB.md)에서 다뤘다. 여기서는 패턴으로서의 요점만: 상태 값은 열거형([types.py:179–186](../../src/profiling/types.py)), 전이는 코드 여러 곳에 있지만 **불변식은 DB 제약 하나**로 지킨다([0002:52–55](../../alembic/versions/0002_profile_runs.py) "결과 상태면 본문 있음").

**우리 코드.** 결과 객체는 `model_copy(update=…)` 로 상태만 바꿔 다시 저장한다([types.py:215–234](../../src/profiling/types.py) 설명, [intake.py:184](../../src/profiling/intake.py) 사용). `attempt` 는 RUNNING 재저장 때만 +1([stores.py:88](../../src/profiling/stores.py)).

**왜.** 코드가 실수해도 DB 가 "결과 없이 결과 상태" 행을 거부한다 — 재전송이 언제나 가능하다는 보장.

**대안.** 상태 기계 라이브러리(transitions) — 전이가 다섯 개뿐이라 과하다. **확인해 보기.** [07 §11](07_데이터와_DB.md) ②.

## 13. 저장 먼저, 전송 다음 + 보상

**개념.** 바깥에 무언가를 **보내기 전에** 그 내용을 먼저 기록해 두면, 보내다 죽어도 "무엇을 보내려 했는지"가 남아 다시 보낼 수 있다(아웃박스 원칙의 가벼운 판). 그리고 뒤 단계가 실패했을 때 앞 단계를 되돌리는 것이 **보상**이다 — 트랜잭션으로 묶을 수 없을 때 쓴다.

**우리 코드.** [pipeline.py:193–206](../../src/profiling/pipeline.py):

```python
# 5) 실행 기록 갱신 — RESULT_READY + 콜백 본문. 저장 실패는 결과를 FAILED로
try:
    store.save(outcome)
except Exception as e:
    return _fail(rq, store, ErrorCode.STORE_FAILED, ..., save=False)
# 6) 수신자 프로필 — 실패하면 FAILED로 되돌린다: 콜백은 나갔는데 Chat이 읽을 프로필이 없는 상태를 만들지 않기 위해.
try:
    recipient_store.upsert(from_outcome(rq, outcome))
except Exception as e:
    return _fail(rq, store, ErrorCode.STORE_FAILED, f"프로필 저장 실패: ...")
```

콜백은 이 함수가 돌아간 **뒤에** 호출자가 보낸다([intake.py:139–143](../../src/profiling/intake.py)). 재전송은 저장된 본문에서 되살린다([intake.py:146–157](../../src/profiling/intake.py), [stores.py:130–137](../../src/profiling/stores.py)). 원자성이 문장 단위인 이유는 [stores.py:13–14](../../src/profiling/stores.py).

**왜.** "콜백은 나갔는데 우리 기록이 없다"가 최악의 상태다 — 재전송도, 감사도 못 한다. 반대(기록은 있는데 콜백이 안 나감)는 재전송으로 복구된다.

**대안.** 한 트랜잭션 — [07 §6](07_데이터와_DB.md)의 이유로 안 한다. 아웃박스 표 + 별도 전송기 — 위키가 v1 에서 DB 큐를 금지. **확인해 보기.** [tests/unit/test_pipeline.py](../../tests/unit/test_pipeline.py) 의 `FakeRecipientStore(fail=True)` 시험 — upsert 실패 뒤 상태가 FAILED 로 저장되는지.

## 14. TTL 캐시 · 이중 검사 잠금 · 스냅샷 교체

**개념.** 자주 읽지만 드물게 바뀌는 것은 **잠깐(TTL) 동안 캐시**한다. 캐시를 다시 채울 때 여러 스레드가 동시에 달려들지 않게 **이중 검사 잠금**을 쓰고, 채운 결과는 **한 번에 교체**해 읽는 쪽이 반쯤 바뀐 것을 못 보게 한다.

**우리 코드.** [catalog.py:243–261](../../src/profiling/catalog.py) `DbCatalogReader.active` — 설명은 [221–226](../../src/profiling/catalog.py), 이중 검사 [253–256](../../src/profiling/catalog.py), 교체 [314–315](../../src/profiling/catalog.py) `self._snapshot = (version, products)`. 한 문장 읽기의 이유는 [180–183](../../src/profiling/catalog.py)([07 §7](07_데이터와_DB.md)).

**왜.** 7.6 한 건이 접수와 슬롯에서 두 번 폴링해 DB 왕복 8번을 쓰던 것을 없앴다([06 §3](06_병목과_성능.md)). 실패는 캐시하지 않아 되살리면 곧바로 회복.

**대안.** 요청마다 읽기(옛 동작, `CATALOG_POLL_TTL_S=0`), 재시작해야 반영되는 영구 캐시 — 새 적재를 못 본다. **확인해 보기.** [tests/integration/test_db_catalog_reader.py:218–240](../../tests/integration/test_db_catalog_reader.py) — 시계를 주입해 0.999초와 1.0초의 차이를 본다.

## 19. 실패 정책 셋 — 죽을 때, 낮춰 살 때, 그냥 갈 때

**개념.** 무엇이 실패했을 때 서비스가 취할 태도는 셋이다. **fail-fast**: 그 상태로 도는 것이 더 위험하면 시작하지 않는다. **degrade**: 핵심 기능은 막되 프로세스는 살려 상태를 보인다. **fail-open**: 보조 장치가 실패하면 없는 셈 치고 진행한다. 어느 것을 고를지는 "실패한 채 진행하면 무엇이 깨지나"로 정한다.

**우리 코드.**

| 실패 | 정책 | 코드 | 이유 |
|---|---|---|---|
| DB 연결·마이그레이션 없음 | **fail-fast** — `RuntimeError`, 앱 안 뜸 | [main.py:56–57, 98–118](../../src/profiling/main.py) | 기록 없이 콜백만 나가는 상태를 만들지 않으려고 |
| 활성 카탈로그 없음 | **degrade** — 앱은 뜨고 7.6 은 503, `/health` 에 이유 | [main.py:59–69](../../src/profiling/main.py) | 사람이 적재하면 재시작 없이 회복 |
| advisory lock 을 못 걺 | **fail-open** — 잠금 없이 진행 | [stores.py:213–218](../../src/profiling/stores.py) | 잠금은 중복을 줄이는 장치이지 접수를 막는 장치가 아니다 |
| 중복 판정용 조회 실패 | **fail-open** — `None` 으로 보고 ANALYZE | [intake.py:238–245](../../src/profiling/intake.py) | 최악이 분석 한 번 더 |
| 워커 안 예외 | **격리** — 그 건만 실패, 워커 생존 | [supervisor.py:131–135](../../src/profiling/supervisor.py) | 한 건이 서비스 전체를 멈추면 안 된다 |

**왜.** 세 태도를 섞어 쓰는 것이 정상이다 — 문제는 "어느 실패에 어느 태도인지"가 코드 곳곳의 `try/except` 에 흩어져 보이지 않는 것이고, 이 표가 그 답이다.

**확인해 보기.** DB 를 끄고(`docker compose stop ai-db`) 앱을 띄우면 `RuntimeError: DB 연결 실패 … → docker compose up -d && uv run alembic upgrade head` 로 죽는다. 카탈로그만 없으면 뜬다(§4).

| 모듈 전역 싱글턴(엔진을 파일 최상단에서 생성) | `lifespan` + `app.state` | import 만 해도 DB 에 붙으면 시험이 무거워진다 |
| 추상 기반 클래스(ABC) 상속 | `Protocol` | 가짜·팀원 어댑터가 상속 없이 꽂히게 |
| ORM 액티브 레코드 / 자동 생성 마이그레이션 | `sa.text` + 손으로 쓴 리비전 | SQL 병합 규칙이 그대로 보이게 |
| 데코레이터 재시도(tenacity) | 호출자의 `while` 루프 | 정책(언제·몇 번·얼마나)이 함수 본문에 보이게 |
| 이벤트 버스 / 옵저버 | 함수 호출 순서 | 단계가 셋(판정·분석·콜백)뿐 |
| DI 컨테이너 라이브러리 | 조립 뿌리 한 함수 | 어댑터가 다섯 개뿐 |
| 목(mock) 라이브러리 | Protocol 모양의 가짜 클래스 | 시험이 "무엇을 부르는지"가 아니라 "무엇이 남는지"를 본다([08 §3](08_테스트.md)) |
| 영속 작업 큐(Celery·Redis) | 메모리 큐 + Backend 재전송 | 위키가 v1 범위 밖으로 둠. 잃는 것은 Backend 재요청이 복구 |
