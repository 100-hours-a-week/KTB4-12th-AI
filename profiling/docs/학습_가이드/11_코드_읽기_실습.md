## 과제 ① 요청 한 건을 끝까지 따라가기 (30분)

**목표.** 7.6 한 건이 로그 다섯 줄과 DB 행 두 개를 남기는 것을 눈으로 본다. 관련 장: [02 §6](02_아키텍처.md), [04 §2](04_통신.md).

1. 콘솔 `http://localhost:8081/console` → "7.6 보내기" 탭. 수신자 `777`, 비선호에 대분류 하나(예: `3 뷰티`)를 넣고 보낸다.
2. **체크포인트 1** — 응답 본문. 무엇이 와야 하나? <details><summary>답</summary>`202` · `{"message":"프로파일 분석이 시작되었습니다.","data":{"recipientUserId":777,"sourceVersion":…,"profileStatus":"PENDING"}}`. 결과 상품은 없다 — 아직 분석 전이다([intake.py:327–330](../../src/profiling/intake.py)).</details>
3. **체크포인트 2** — AI 터미널의 첫 줄. <details><summary>답</summary>`profiling.intake: 7.6 접수 recipient=777 source_version=… disliked=1 reviews=0 pref=False` ([intake.py:316](../../src/profiling/intake.py)). 이 줄은 아직 이벤트 루프에서 찍힌다.</details>
4. **체크포인트 3** — 둘째 줄. 판정 결과와 이유는? <details><summary>답</summary>`7.6 중복 판정 recipient=777 … → analyze (첫 접수)` — `decide(None, …)` 의 첫 분기([intake.py:208–209](../../src/profiling/intake.py)). 여기부터는 워커 스레드다.</details>
5. **체크포인트 4** — 분석 결과 줄에서 `pool=` 뒤 숫자 두 개는? <details><summary>답</summary>`profile … → RESULT_READY pool=30/30 disliked=1 …` — 뽑은 수/상한. 예시 카탈로그 111건에서 뷰티를 빼도 30개는 남는다. 비선호를 여러 개 넣어 30 아래로 떨어뜨려 본다.</details>
6. **체크포인트 5** — 콜백 줄. 시도 번호와 상태는? <details><summary>답</summary>`7.7 콜백 결과 … 시도 1/3 → DELIVERED` ([intake.py:176](../../src/profiling/intake.py)). 가짜 BE 가 ok 모드라 한 번에 200.</details>
7. **체크포인트 6** — 콘솔 "DB" 탭. 두 표에 각각 몇 행, 어떤 값? <details><summary>답</summary>`profile_runs` 1행: `status=DELIVERED`, `attempt=1`, `callback_attempts=1`, `callback_payload` 에 상품 30개, `callback_hash` 있음. `recipient_profiles` 1행: `disliked_tags=["뷰티"]`, `disliked_categories=[{category_id:3, category_name:"뷰티"}]`, `preferred_tags=[]`(v1).</details>
8. **질문.** 같은 수신자 `777` 로 "sourceVersion 자동 증가"를 켠 채 한 번 더 보내면 두 표는 어떻게 되나? <details><summary>답</summary>새 번호라 `decide` 는 `첫 접수`(그 번호로는 처음) → analyze. `profile_runs` 는 행이 **하나 더**(키가 (수신자, 버전)), `recipient_profiles` 는 **같은 행이 갱신**(수신자당 한 행, `source_version` 이 올라감 — [stores.py:282–291](../../src/profiling/stores.py)).</details>

## 과제 ② 실패를 주입하고 복구를 보기 (25분)

**목표.** 콜백 5xx 의 즉시 재시도, 미전달 상태, 같은 번호 재전송을 본다. 관련 장: [04 §7–§8](04_통신.md).

1. 콘솔 "7.9·상태" 탭에서 실패 주입 모드를 **500** 으로. (또는 `curl -X PUT localhost:8081/console/mode -H 'content-type: application/json' -d '{"mode":"500"}'`)
2. 수신자 `778` 로 7.6 을 한 건 보낸다.
3. **체크포인트 1** — AI 로그에 콜백 줄이 몇 개, 사이의 경고는? <details><summary>답</summary>`시도 1/3 → RESULT_READY (CALLBACK_UNREACHABLE: 500 …)` → `7.7 미전달 … 0.5초 뒤 다시 보낸다 (2/3)` → `시도 2/3 → RESULT_READY` → `… 2.0초 뒤 … (3/3)` → `시도 3/3 → RESULT_READY`. 총 약 2.5초([intake.py:172–182](../../src/profiling/intake.py)).</details>
4. **체크포인트 2** — `curl -s localhost:8000/health` 의 `store.undelivered` 와 DB 행. <details><summary>답</summary>`undelivered: 1`. `profile_runs` 행은 `status=RESULT_READY`, `callback_attempts=3`, `error={"code":"CALLBACK_UNREACHABLE", …}`. 본문은 저장돼 있다(그래서 재전송이 가능하다).</details>
5. 모드를 **ok** 로 되돌리고, 자동 증가를 **끈** 채 같은 수신자 `778`·같은 번호로 다시 보낸다.
6. **체크포인트 3** — 로그 두 줄. <details><summary>답</summary>`7.6 중복 판정 … → resend (RESULT_READY — 저장된 결과 재전송)` · `7.7 재전송 … (기존 RESULT_READY · 재분석 없음)` · `시도 1/3 → DELIVERED`. `profile … → RESULT_READY` 줄이 **없다** — 재분석하지 않았다.</details>
7. **체크포인트 4** — 이제 행의 `attempt`·`callback_attempts` 는? <details><summary>답</summary>`attempt=1`(분석은 한 번), `callback_attempts=4`(3 + 1, `greatest` 가 아니라 이전 값에 더한 값을 저장 — [intake.py:184](../../src/profiling/intake.py) `outcome.callback_attempts + attempts`), `status=DELIVERED`, `undelivered=0`.</details>
8. **질문.** 모드가 500 이 아니라 **409** 였다면 3번 체크포인트는 어떻게 달라졌을까? <details><summary>답</summary>재시도 없이 한 번에 `→ SUPERSEDED (CALLBACK_STALE …)`. `undelivered` 는 0 이다 — SUPERSEDED 는 "결과 있음·미전달"이 아니라 "폐기됨"으로 센다([backend.py:71–72](../../src/profiling/backend.py), [stores.py:266](../../src/profiling/stores.py)).</details>

## 과제 ③ 시험 하나를 추가하기 (20분)

**목표.** 판정표에 행을 더해 시험을 돌리고, 관습(파일 docstring·README 표)을 따른다. 관련 장: [08 §8–§9](08_테스트.md).

1. [tests/unit/test_intake_dedupe.py:54–64](../../tests/unit/test_intake_dedupe.py) 의 `parametrize` 목록 끝에 한 줄:
   ```python
   (_outcome(RunStatus.SUPERSEDED, search=False), ANALYZE),           # 결과 상태인데 본문이 없다 — 방어
   ```
2. `uv run pytest tests/unit/test_intake_dedupe.py -q`
3. **체크포인트 1** — 몇 개가 통과하나? <details><summary>답</summary>`21 passed`(원래 20). `existing.search is None` 분기([intake.py:219–220](../../src/profiling/intake.py))가 상태와 무관하게 ANALYZE 를 준다.</details>
4. 이제 **틀린** 기대값으로 바꿔 본다: `ANALYZE` → `RESEND`. 돌리면?
5. **체크포인트 2** — 실패 메시지에서 무엇을 읽을 수 있나? <details><summary>답</summary>`assert action == expected` 가 `'analyze' == 'resend'` 로 깨지고, `why` 에 `SUPERSEDED인데 저장된 결과가 없음 — 재분석` 이 보인다. "이유" 를 같이 돌려주는 설계의 값이 여기서 나온다.</details>
6. 되돌린다(`git checkout tests/unit/test_intake_dedupe.py`) — 또는 남기려면 README §4 표의 `test_intake_dedupe.py` 개수를 21 로, `uv run ruff check tests` 를 통과시키고 커밋한다.

## 과제 ④ 하네스로 100건을 재고 표 읽기 (25분)

**목표.** 부하 하네스를 한 번 돌리고 요약 표의 숫자를 읽는다. 관련 장: [06 §1](06_병목과_성능.md), [05 §4](05_동시성.md).

1. AI 를 `--reload` **없이** 다시 띄운다(부하 중 재시작 방지). 파일 카탈로그면 `--expect-slots 1` 만 맞으면 된다.
2. ```bash
   uv run python -m tools.loadtest.run --n 100 --concurrency 100 --base 900001 --cleanup --yes --expect-slots 1 --label 실습 --out tools/loadtest/results/실습.json
   ```
3. **체크포인트 1** — `7.6 응답` 줄. 어떤 범위면 정상인가? <details><summary>답</summary>`{'202': 100}`, p50 80~250ms, 10초 초과 0. 100건이 한꺼번에 오면 이벤트 루프가 순서대로 받으므로 마지막 건은 앞의 99건 뒤에 202 를 받는다 — p95 가 p50 의 두 배쯤인 이유.</details>
4. **체크포인트 2** — `/health` 줄. <details><summary>답</summary>실패 0, 최대 100ms 안팎. 09-28 이전이었다면 정상 콜백에서도 최대 0.5초, 느린 콜백이면 10초 타임아웃이 났다.</details>
5. **체크포인트 3** — `완료` 줄의 처리량과 `큐 최대`. 왜 큐가 60~80 까지 쌓이나? <details><summary>답</summary>접수(초당 수백 건)가 배출(초당 100~200건)보다 빠르다. 워커가 첫 건들을 처리하는 0.1~0.3초 동안 나머지가 큐에 쌓였다가 1초 안에 빠진다. 큐 상한 200 이 넉넉한 이유이자, 300건 버스트면 닿는 이유([06 §2](06_병목과_성능.md)).</details>
6. **체크포인트 4** — `DB` 줄의 커넥션 최대. <details><summary>답</summary>2~5. 잠금 커넥션 1 + 첫 순간의 폴링·`/health` 용 리미터 커넥션. 풀 상한 15 에 한참 못 미친다([05 §8](05_동시성.md)).</details>
7. **질문.** 같은 명령을 `--fake-mode 500 --post-timeout 300 --wait 320` 로 돌리면 `완료` 줄의 "전부 종료까지" 는 몇 초쯤일까? 돌리기 전에 계산해 본다. <details><summary>답</summary>약 254초 — 슬롯 1 × 한 건 2.5초(0.5 + 2 + 시도 셋) × 100. 그동안 `/health` 는 계속 답한다. 확인은 [09-29 §4.4](../부하_시험_결과_2026-09-29.md).</details>

## 졸업 질문 다섯 (답을 말로 설명할 수 있으면 끝)

1. `pipeline.py` 가 `stores.py` 를 import 하지 않는데 어떻게 DB 에 저장하나? <details><summary>답</summary>포트 모양(`ProfileRunStore`)의 객체를 인자로 받고, 그 객체는 `main.lifespan` 이 만든 `DbProfileRunStore` 다([02 §1, §5](02_아키텍처.md)).</details>
2. 토큰이 틀리고 본문도 틀린 7.6 은 401 인가 400 인가? <details><summary>답</summary>401. JSON 파싱 → 의존성(토큰) → 본문 검증 순서([04 §4](04_통신.md)).</details>
3. 콜백이 느릴 때 09-28 이전에 `/health` 가 멈춘 이유를 한 문장으로. <details><summary>답</summary>슬롯 대기가 스레드풀 토큰 40개를 쥐고 있어 같은 풀을 쓰는 `/health` 가 줄 뒤에 섰다([05 §2](05_동시성.md)).</details>
4. 같은 (수신자, 버전)이 동시에 두 워커에 오르면 분석이 두 벌 도는 것을 무엇이 막나? <details><summary>답</summary>PostgreSQL advisory lock — 둘째는 `pg_try_advisory_lock` 이 false 라 조용히 끝난다([05 §7](05_동시성.md)).</details>
5. 결과를 저장한 뒤 프로필 upsert 가 실패하면 실행 기록은 어떤 상태가 되고 Backend 는 무엇을 받나? <details><summary>답</summary>FAILED 로 되돌린다(보상). Backend 는 아무것도 받지 않고(침묵) PENDING 타임아웃 뒤 같은 번호로 다시 보낸다([03 §13](03_디자인_패턴.md), [04 §2](04_통신.md)).</details>
