## 0. 과한지 가르는 네 가지 질문

"오버엔지니어링"은 **지금 없는 문제를 미리 풀어 둔 비용**이다. 이름 있는 원칙이 셋 있다.

- **YAGNI** (You Aren't Gonna Need It) — Kent Beck·Ron Jeffries, 익스트림 프로그래밍(1990년대 말). 필요해질 때 넣어라.
- **세 번의 법칙** (Rule of Three) — Don Roberts 가 말하고 Martin Fowler 가 『Refactoring』(1999)에 실었다. 같은 것이 세 번 나올 때 추상화하라. 둘째 구현이 실제로 있어야 추상화가 값을 한다.
- **추측성 일반화** (Speculative Generality) — 같은 책의 코드 냄새. "언젠가 필요할 것 같아서" 넣은 훅·인자·추상 클래스.

패턴 하나를 볼 때 이 넷을 묻는다.

| # | 질문 | 답이 "예"면 |
|---|---|---|
| Q1 | **지우면 무엇이 깨지나?** — 시험·기록된 사고·Backend 계약 중 하나라도 걸리나 | **필수** |
| Q2 | **측정되거나 기록된 필요가 있나?** — 부하 결과 수치, 이슈 번호, BE 합의 | **적정** (미래를 위해 넣었으면 의심) |
| Q3 | **둘째 구현이 실제로 있나?** — 가짜(test double)도 센다. 배포에서 절대 안 쓰이는 구현은 반만 센다 | 없으면 추상화는 비용만 |
| Q4 | **개념 비용은?** — 처음 읽는 사람이 이해하는 데 몇 분, 줄 수 몇 줄 | 이득보다 크면 과함 |

## 1. 의존성 주입 (Dependency Injection)

**정의.** 객체가 협력자(DB 접근, HTTP 클라이언트)를 스스로 만들지 않고 **밖에서 받는다.** 만드는 책임이 한 곳(조립 뿌리)으로 모이고, 받는 쪽은 진짜와 가짜를 구분하지 않는다.

**유래.** 뿌리는 **제어의 역전**(Inversion of Control) — Ralph Johnson·Brian Foote, "Designing Reusable Classes"(1988)에서 프레임워크가 애플리케이션 코드를 부르는 구조를 설명하며 썼다("할리우드 원칙: 우리가 부를 테니 전화하지 마라"). "의존성 주입"이라는 이름은 **Martin Fowler, 2004**, "Inversion of Control Containers and the Dependency Injection pattern" — 당시 Java 의 Spring(2003)·PicoContainer 가 하는 일을 IoC 라는 넓은 말과 구분하려고 붙였다. 생성자 주입·세터 주입·인터페이스 주입 세 형태도 그 글에서 정리됐다.

**우리가 풀려던 문제.** 업무 함수 `pipeline.profile()` 이 안에서 `DbProfileRunStore(engine)` 을 만들면 **단위 시험이 DB 를 찾는다.** 155개 단위 시험이 0.01초에 도는 것은 인자로 받기 때문이다([03 §1](03_디자인_패턴.md)). 두 번째 문제는 "어디서 만들었지" — 만드는 곳이 `main.lifespan` 하나라 답이 한 줄이다([02 §5](02_아키텍처.md)).

**없애면.** 단위 시험 대부분이 PostgreSQL 을 요구해 통합 시험이 된다(0.01초 → 수 초). 사람들은 느린 시험을 안 돌린다. 그리고 카탈로그를 파일에서 DB 로 바꿀 때 `pipeline.py` 가 바뀌었을 것이다 — 실제로는 한 줄도 안 바뀌었다([DB_전환_설명](../DB_전환_설명.md)).

**판정 — 필수.** 비용은 긴 인자 목록(`extract_and_pool` 8개, `profile` 6개)뿐이다. **과해지는 신호:** DI 컨테이너 라이브러리를 들이는 것. 어댑터 다섯 개를 자동 배선하면 "어디서 만들었지"가 마법이 된다. 그 신호는 어댑터가 열 개를 넘고 조립 함수가 100줄을 넘을 때 온다 — 지금 `lifespan` 은 45줄이다.

## 2. 구조적 타이핑 — `typing.Protocol`

**정의.** 타입 호환을 "무엇을 상속했나"가 아니라 **"어떤 메서드를 가졌나"(모양)** 로 판정한다. 명시적 선언 없이 모양만 맞으면 그 타입이다.

**유래.** 파이썬의 **덕 타이핑**(오리처럼 걷고 꽥꽥거리면 오리) 은 언어 초기부터의 관용이고, 이름은 2000년 comp.lang.python 에서 Alex Martelli 가 굳혔다. 그것을 **정적으로** 검사하는 구조적 서브타이핑은 OCaml, Go 의 인터페이스(2009), TypeScript(2012)가 먼저였고, 파이썬은 **PEP 544 "Protocols: Structural subtyping (static duck typing)"** — Ivan Levkivskyi·Jukka Lehtosalo·Łukasz Langa, 2017 → Python 3.8(2019). `@runtime_checkable` 도 같은 PEP 다. 반대편(명목적 타이핑)은 Java 의 `implements`, 파이썬의 ABC(PEP 3119, 2007).

**우리가 풀려던 문제.** `pipeline` 이 구현 모듈(`stores`·`catalog`·`backend`)을 import 하지 않고도 그 모양을 요구할 수 있어야 한다([02 §4](02_아키텍처.md)). 그리고 시험의 가짜 7개와 팀원 검색기 어댑터가 **우리 클래스를 상속하지 않고** 꽂혀야 한다 — 팀원 코드가 우리 기반 클래스에 묶이는 순간 저장소 둘이 결합한다.

**없애면.** ABC 로 바꾸면 가짜 7개에 `class Fake(ProfileRunStore):` 한 줄씩 — 대단한 비용은 아니다. 진짜 손해는 다른 데 있다: Protocol 을 아예 없애면 `pipeline` 이 `from profiling.stores import DbProfileRunStore` 를 하게 되고, 그 순간 업무 코드가 DB 코드를 안다.

**판정 — 적정. `@runtime_checkable` 은 선택.** Protocol 네 개(112줄, 절반이 설명문)는 Q3 를 통과한다 — 둘째 구현이 진짜로 있다(가짜 7개 + DB/파일 두 카탈로그). 데코레이터는 시험 5곳의 `isinstance(obj, CatalogReader)` 를 위해서만 있고, 그 검사는 **메서드 이름만** 본다(서명은 안 본다). 지워도 깨지는 건 그 assert 다섯 줄이다. **과해지는 신호:** 구현이 하나뿐이고 가짜도 없는 것을 포트로 뽑는 것. 우리는 `Supervisor` 를 포트로 안 뽑았다 — 시험은 `FakeSupervisor` 를 쓰지만 Protocol 없이 모양만 맞춘다. 그게 맞다.

## 3. 전략 (Strategy)

**정의.** 같은 일을 하는 알고리즘(구현)이 여럿일 때 각각을 객체로 캡슐화하고, 부르는 쪽은 공통 인터페이스만 보며 **어느 것을 쓸지는 바깥에서 고른다.**

**유래.** **GoF, 『Design Patterns』(1994)** — Gamma·Helm·Johnson·Vlissides. 행위 패턴 23개 중 하나. 원래 예는 텍스트 줄바꿈 알고리즘 교체. 파이썬에서는 클래스 없이 함수를 넘겨도 같은 뜻이라 "패턴"이라 부르기도 민망할 만큼 가볍다.

**우리가 풀려던 문제.** 09-21 까지 카탈로그는 파일(JSON 111건)이었고, 09-23 에 DB(`ai_catalog`, 4,231건)로 바뀌었다. 배포 컨테이너에는 파일이 없고, 로컬·시험은 DB 없이 돌고 싶었다. 그래서 `CATALOG_SOURCE=file|db` 로 고른다([03 §3](03_디자인_패턴.md)).

**없애면.** `FileCatalogReader` 를 지우면 깨지는 것: 단위 시험 파일 4개(`test_catalog`·`test_catalog_fixture`·e2e·`test_db_stores` 의 일부), 도구 3개(`make_sample`·`fetch_export --compare`·`fake_backend`). 단위 시험 쪽은 `ProductRecord` 리스트를 직접 만드는 가짜로 바꾸면 된다 — `test_pipeline.py` 는 이미 그렇게 한다. 도구는 DB 를 읽게 바꾼다. 합쳐서 반나절.

**판정 — 과할 수 있음, 정리 후보.** Q3 에서 걸린다: 둘째 구현(파일)은 **배포에서 절대 안 쓰인다.** 게다가 파일 판은 원형 변환 규칙(`_provisional_product_id` — 수집처 ID 에서 숫자를 떼 임시 번호를 만드는 것)을 갖고 있고, 팀원의 [INTEGRATION.md](../../../product-search/INTEGRATION.md) 도 "그 임시 변환을 운영 매핑으로 쓰지 말라"고 짚었다. 두 구현을 같이 고쳐야 하는 비용은 지금도 낸다 — v2 검색 연결에서 `ProductRecord` 에 필드 둘을 더하면 파일 판은 `None` 으로 채워야 한다. **반대 근거:** 파일 카탈로그가 있어야 DB 없이 앱을 띄워 콘솔로 7.6 을 눌러 볼 수 있다(신입 온보딩). 그 용도라면 111건 JSON 을 **DB 에 넣는 스크립트**(`load_catalog` 이 이미 있다)가 같은 일을 한다. 판단은 사용자 몫이고, 내 의견은 "v3 착수 전에 지운다"다.

## 4. 널 오브젝트 (Null Object)

**정의.** "없음"을 `None` 이 아니라 **같은 인터페이스를 가진 객체**로 표현한다. 그 객체는 아무것도 안 하거나, 정해진 방식으로 실패한다. 쓰는 쪽의 `if x is None` 이 사라진다.

**유래.** **Bobby Woolf, "Null Object", PLoP 1996** (책으로는 『Pattern Languages of Program Design 3』, 1998). GoF 23개에는 없다. Fowler 『Refactoring』(1999)의 "Introduce Null Object" 로 널리 퍼졌다. 원래 동기는 GUI 코드의 `if (view != null) view.update()` 반복.

**우리가 풀려던 문제.** 기동 때 카탈로그 로드가 실패해도 앱은 떠야 한다(§19 의 degrade). `app.state.catalog` 를 `None` 으로 두면 `intake`(접수)와 `/health` 두 곳이 `None` 을 검사해야 하고, 자리가 늘면 빠뜨린다. `_NoCatalog` 는 `active()` 가 항상 `NoActiveCatalog` 를 던지므로 두 곳이 정상 경로와 같은 코드로 503 을 낸다([03 §4](03_디자인_패턴.md)).

**없애면.** `Optional[CatalogReader]` + `if catalog is None` 두 곳. 지금은 두 곳뿐이라 그것도 된다.

**판정 — 선택.** 9줄이고 이해 비용도 9줄이다. 이 패턴의 진짜 위험은 딴 데 있다: 널 오브젝트가 **실패를 삼켜** 조용히 아무것도 안 하면 버그가 숨는다. 우리 것은 항상 예외를 던지므로(삼키지 않음) 그 함정은 피했다. **과해지는 신호:** 널 오브젝트에 분기가 생기기 시작할 때(`if self.reason == …`) — 그건 이미 진짜 구현이다.

## 5. 리포지토리 (Repository)

**정의.** 데이터 접근을 **컬렉션처럼 보이는 인터페이스**(save·get·delete) 뒤에 감춘다. 나머지 코드는 SQL 도, 표 이름도 모른다.

**유래.** **Martin Fowler, 『Patterns of Enterprise Application Architecture』(2002)** — "도메인과 데이터 매핑 층 사이를 컬렉션 같은 인터페이스로 중재한다". **Eric Evans, 『Domain-Driven Design』(2003)** 이 애그리거트 단위의 저장소로 대중화했다. 그 뒤 ORM 프레임워크(Hibernate, Spring Data)가 "리포지토리 = 자동 생성 CRUD" 로 뜻을 좁혔지만, 원래 뜻은 그저 "접근을 한 곳에".

**우리가 풀려던 문제.** SQL 이 코드 여기저기 흩어지면 표를 바꿀 때 전체를 grep 해야 한다. 지금 SQL 문장은 `stores.py` 상수 열 개 남짓이고, `pipeline` 은 `store.save(outcome)` 만 안다. 시험은 dict 하나짜리 가짜 저장소로 돈다([03 §5](03_디자인_패턴.md)).

**없애면.** `pipeline.profile()` 안에 `sa.text("insert into …")` 가 들어오고, 그 순간 단위 시험이 DB 를 요구한다(§1 과 같은 손해).

**판정 — 필수.** 그리고 **가벼운 판**이다: ORM 도, 제네릭 CRUD 기반 클래스도 없다. upsert 의 병합 규칙(`coalesce`·`greatest`·`CASE`)이 SQL 로 그대로 보이는 것이 오히려 이득이다([07 §3](07_데이터와_DB.md)). **과해지는 신호:** 저장소가 `BaseRepository[T]` 같은 제네릭 기반 클래스로 자라거나, 표 하나에 메서드가 스무 개를 넘을 때. 지금은 7 + 3 이다.

## 6. DTO 와 부패 방지 매퍼

**정의.** **DTO**(Data Transfer Object)는 프로세스·네트워크 경계를 넘는 데이터 묶음 — 메서드 없이 필드만. **부패 방지 계층**(Anti-Corruption Layer)은 바깥 시스템의 모델이 우리 모델을 오염시키지 않게 사이에 둔 변환층이다.

**유래.** DTO — Sun 의 **Core J2EE Patterns(2001)** 에서 "Transfer Object"(당시 이름은 Value Object), 원격 호출(EJB) 한 번에 여러 필드를 묶어 보내려는 성능 동기였다. Fowler PoEAA(2002)가 DTO 라는 이름으로 정리. ACL — **Evans, DDD(2003)**, 레거시 시스템과 통합할 때 "그쪽 언어를 우리 언어로 번역하는 층" 으로 소개했다.

**우리가 풀려던 문제.** Backend 계약(camelCase, 위키 문서 1)은 우리 것이 아니고 자주 바뀐다. 실제로 09-22~25 사이에 `views`/`viewCount`/`view_count` 이름 흔들림, `available`(bool) → 3값, 7.9 export 의 필드 차이가 있었고 전부 `schemas.py` 의 별칭과 변환 함수 다섯 곳으로 흡수됐다([03 §6](03_디자인_패턴.md)). SQL 열 이름·로그·시험은 흔들리지 않았다.

**없애면.** DTO 를 내부에서 그대로 쓰면 `recipientUserId` 가 SQL·로그·시험까지 퍼지고, 계약이 바뀔 때마다 전체 grep. 대신 파일 하나(`types.py` 317줄)와 변환 코드 ≈150줄, [이름_대조표](../../이름_대조표.md)의 유지가 사라진다.

**판정 — 적정, 비용 있음.** 여기가 **사용자가 판단해야 할 지점**이다. 지금 `ProfileRequest`(내부) 와 `ProfileExtractRequest`(DTO) 는 **이름만 다르다**(snake/camel). 이름 변환만을 위한 이중화라면 12주 프로젝트에 과하다는 주장이 가능하다. 내가 유지에 손을 드는 이유는 하나다 — v3 에서 내부형은 검증기 출력(3축 태그·판정 로그)과 모델 출력을 담게 되어 DTO 와 **갈라진다**(`types.py` 의 `ExtractDraft`·`ValidationResult` 는 이미 그 자리다). 갈라질 것이 확실하면 지금 나누는 게 싸다. 확실하지 않으면 YAGNI 다. **과해지는 신호:** 두 자료형이 필드 1:1 인 채로 반년이 가면.

## 7. 관대한 읽기 / 엄격한 쓰기

**정의.** 받을 때는 너그럽게(모르는 필드 무시, 별칭 허용), 보낼 때는 보수적으로(정해진 필드만).

**유래.** **Jon Postel, RFC 761(1980), TCP 명세** — "자기가 하는 일에는 보수적이고, 남에게서 받는 것에는 관대하라"(견고성 원칙, Postel's Law). 서비스 진화 맥락에서는 **Fowler 의 "Tolerant Reader"(2011, bliki)**. 반론도 알아 두어야 한다: **RFC 9413 (2023) "Maintaining Robustness Protocols"** 는 관대함이 오류를 **숨겨** 잘못된 구현이 생태계에 굳어 버린다고 경고한다 — 관대하되 **드러내라**는 것이 현대의 절충이다.

**우리가 풀려던 문제.** 연동 초기에 Backend 가 필드를 하나 더 보냈다고 400 을 내면 그날 시험이 멈춘다. 반대로 우리가 보내는 7.7 에 태그가 섞이면 DR-035 위반이다. 그래서 7.6 은 `allow` + **경고 로그**(`CONTRACT_7_6_UNKNOWN_FIELD` — RFC 9413 의 "드러내라"가 이것), 7.7 은 `forbid`, 7.9 는 `ignore` + 별칭([03 §7](03_디자인_패턴.md)).

**없애면.** 전부 `forbid` 면 FE 시험 시나리오 중 절반이 400 으로 시작했을 것이다(09-25 시험 결과 참고).

**판정 — 적정.** 설정 3줄과 로그 한 줄. **과해지는 신호:** 경고 로그가 몇 주째 쌓이는데 아무도 안 보는 것 — 그때 관대함은 RFC 9413 이 말한 숨김이 된다.

## 8. 컨텍스트 매니저

**정의.** 자원의 획득과 해제를 언어 구문(`with`)에 묶어, 예외가 나도 해제가 보장되게 한다.

**유래.** **PEP 343 "The with statement"(2005, Guido van Rossum·Nick Coghlan)** → Python 2.5(2006). 뿌리는 C++ 의 **RAII**(Resource Acquisition Is Initialization, Stroustrup, 1980년대 중반 — 소멸자가 자원을 놓는다)와 Smalltalk 의 **Execute Around Method**(Kent Beck, 『Smalltalk Best Practice Patterns』, 1997). 파이썬은 소멸자 시점이 불확실해서(가비지 컬렉션) 명시적 블록이 필요했다.

**우리가 풀려던 문제.** advisory lock 은 **세션 잠금**이라 커넥션이 살아 있는 한 풀리지 않는다. 해제를 한 번 빠뜨리면 그 (수신자, 버전) 키가 영영 막힌다 — 09-27 잠금 이슈 셋 중 하나가 정확히 이 계열이었다([이슈 2026-09-27_1633](../issues/2026-09-27_1633_advisory-lock/README.md)). `with store.run_lock(...)` 은 예외가 나도 `finally` 에서 푼다([03 §8](03_디자인_패턴.md)).

**없애면.** 호출자마다 `try/finally`. 언젠가 빠뜨린다.

**판정 — 필수.** 비용 0 인 언어 관용구다. 여기서 배울 것은 패턴이 아니라 "잠금은 왜 세션 단위인가"([05 §7](05_동시성.md))다.

## 9. 명령 객체 + 워커 풀 (상한 큐 · 포이즌 필)

**정의.** 네 가지가 겹쳐 있다. **명령**(Command): 요청을 값(`(함수, 인자)`)으로 만들어 실행 시점과 주체를 분리. **생산자-소비자 큐**: 넣는 쪽과 꺼내는 쪽을 큐로 잇는다. **워커 풀**: 고정 수의 스레드가 큐를 비운다. **상한 큐**(bounded queue)와 **포이즌 필**: 큐가 차면 거절해 배압을 걸고, 종료는 특별한 값을 큐에 넣어 워커가 스스로 멈추게 한다.

**유래.** Command — GoF(1994). 생산자-소비자와 유한 버퍼 — **Dijkstra, 1965**("Cooperating Sequential Processes", 세마포어). 스레드 풀 — Java 의 `Executor` 프레임워크(Doug Lea, `util.concurrent` 1998 → JDK 5, 2004). 포이즌 필 — **Goetz 외, 『Java Concurrency in Practice』(2006)** §7.2.3. "배압"(backpressure)이라는 말은 Reactive Streams(2013~2015)가 굳혔다.

**우리가 풀려던 문제.** **09-28 굶음.** 슬롯을 기다리는 실행이 anyio 기본 스레드풀 토큰(40)을 쥔 채 잠들어, 슬롯이 2.5초만 돼도 `/health` 가 150초 무응답, 그 사이 들어온 7.6 이 34.5초(Backend 10초 타임아웃 초과). 대기를 **큐**로 옮기고 워커 스레드가 꺼내 실행하게 하자 `/health` 실패 0·최대 95ms, 추가 접수 6.5ms([부하 결과 09-29 §3.1](../부하_시험_결과_2026-09-29.md), [05 §4](05_동시성.md)).

**없애면.** `BackgroundTasks` 나 요청마다 `threading.Thread` — 상한도 통계도 없고, 굶음이 재발하거나 메모리가 무한 큐가 된다.

**판정 — 필수.** Q2 를 가장 강하게 통과한다(측정 → 수정 → 재측정). 비용은 172줄과 종료 의미론("큐는 버리고 실행 중만 5초 기다린다")의 이해. **과해지는 신호:** 브로커(Celery·RQ·Redis)를 들이는 것. 프로세스 하나에 워커 4개면 메모리 큐가 맞고, 위키도 v1 에서 DB 큐를 금지했다. 브로커가 필요해지는 때는 프로세스 2개 이상이 **한 큐를 공유**해야 할 때다.

## 10. 재시도 · 백오프

**정의.** 일시적 실패를 **간격을 늘리며 제한된 횟수** 다시 시도한다. 영구 실패(4xx)에는 하지 않는다.

**유래.** 지수 백오프는 **Ethernet 의 CSMA/CD(Metcalfe·Boggs, 1976)** — 충돌 뒤 무작위로 늘어나는 대기(ALOHAnet, 1971 이 선례). 분산 시스템 관용으로는 **AWS 의 "Exponential Backoff And Jitter"(Marc Brooker, 2015)** 가 "지터 없는 백오프는 재시도가 동시에 몰린다"를 보였다. 타임아웃·서킷 브레이커·격벽 같은 안정성 패턴 묶음은 **Michael Nygard, 『Release It!』(2007)**.

**우리가 풀려던 문제.** 7.7 콜백이 Backend 의 5xx·타임아웃으로 실패하면 곧바로 RESULT_READY 로 남겨 Backend 의 재요청(10분 뒤)을 기다려야 했다. 순간 장애는 0.5초·2초 뒤에 대개 회복되므로 같은 슬롯에서 즉시 3회를 시도하고, 그래도 안 되면 그때 재전송 대상으로 남긴다([03 §10](03_디자인_패턴.md), [BE 전달 §2](../BE_전달_2026-09-27.md)).

**없애면.** 순간 장애 하나가 10분 지연이 된다. 반대로 상한이 없으면 슬롯이 영원히 묶인다 — 최악 대기 17.5초를 계산해 두었다.

**판정 — 적정.** 15줄 루프, `sleep` 주입으로 시험 0초. **지터가 없는 것이 맞다** — 지터는 클라이언트 여럿이 동시에 재시도할 때의 처방이고 우리 클라이언트는 하나다. **서킷 브레이커가 없는 것도 맞다** — 호출 대상이 하나(Backend)고 100건/분이다. **과해지는 신호:** 재시도 라이브러리 + 브레이커 + 지터 — 호출 대상이 둘 이상(v2 의 검색기!)이 되면 다시 볼 것. v2 설계의 "검색 실패 → v1 대체"가 브레이커의 절반 역할이다.

## 11. 순수 판정 함수

**정의.** 입력만으로 출력이 정해지고 부작용(DB·시간·네트워크)이 없는 함수. 결정을 순수 함수로 빼면 **표 하나**로 시험할 수 있고, 같은 입력엔 언제나 같은 답(멱등의 바탕)이다.

**유래.** "참조 투명성"은 철학자 **Quine(『Word and Object』, 1960)** 의 말을 **Christopher Strachey(1967, "Fundamental Concepts in Programming Languages")** 가 프로그래밍에 가져왔다. **결정표**(decision table)는 1960년대 업무 프로그래밍의 도구(CODASYL DETAB-X, 1965). "멱등"은 대수학의 **Benjamin Peirce(1870)**, HTTP 에서는 멱등 메서드(RFC 9110).

**우리가 풀려던 문제.** 같은 (수신자, 버전) 요청이 다시 왔을 때 재분석·재전송·무시 중 무엇을 할지 — 규칙 10가지. 잠금 안의 `if` 로 쓰면 시험에 DB 와 잠금이 필요하다. `decide(existing, input_hash, now=…)` 로 빼니 시험이 표 10줄이고, 함수가 "이유" 문자열을 같이 돌려줘 로그가 곧 설명이다([03 §11](03_디자인_패턴.md), [04 §8](04_통신.md)).

**없애면.** 규칙을 바꿀 때 회귀를 못 잡는다. 실제로 09-25 에 "RUNNING 이 300초 지나면 재분석" 규칙이 추가됐고 표 한 줄로 들어갔다.

**판정 — 적정.** 비용 0 인 스타일이다. **과해지는 신호:** 없다. 굳이 하나면 순수성을 위해 인자가 폭발하는 것(§17).

## 12. 상태 기계 + DB 불변식

**정의.** 상태 집합과 허용 전이를 정하고(상태 기계), "항상 참이어야 하는 조건"(불변식)은 **DB 제약**으로 강제한다. 코드가 실수해도 DB 가 거부한다.

**유래.** 유한 상태 기계 — **Mealy(1955)·Moore(1956)** 의 순차 회로 모델(개념은 Turing 1936 이전). GoF 의 State 패턴(1994)은 상태별 클래스인데 우리는 그것은 안 쓴다. 관계형 무결성 제약 — **Codd(1970)**, SQL-92 의 `CHECK`. "잘못된 상태를 표현 불가능하게 만들라"(make illegal states unrepresentable) — **Yaron Minsky, Jane Street, 2011**(OCaml 맥락).

**우리가 풀려던 문제.** `RUNNING → RESULT_READY → DELIVERED | SUPERSEDED | FAILED`. "결과 상태면 콜백 본문이 있다"가 깨지면 재전송 때 본문이 없어 터진다. 코드 다섯 곳이 상태를 바꾸는데 그 다섯 곳이 전부 옳다고 믿는 대신 `0002` 의 CHECK 하나가 지킨다([07 §9](07_데이터와_DB.md), [03 §12](03_디자인_패턴.md)).

**없애면.** 코드 버그로 본문 없는 RESULT_READY 행이 생기고, 재전송이 `None` 을 보내거나 예외로 죽는다.

**판정 — 적정.** CHECK 두 개, `StrEnum` 다섯 값. **과해지는 신호:** 상태 기계 라이브러리(`transitions`), 상태별 클래스 — 전이 다섯 개엔 과하다. 열 개를 넘고 전이마다 훅이 필요해지면 그때.

## 13. 저장 먼저, 전송 다음 + 보상

**정의.** 바깥으로 보내기 **전에** 보낼 내용을 영속화한다(아웃박스 원칙). 트랜잭션으로 묶을 수 없는 여러 단계에서 뒤 단계가 실패하면 앞 단계를 **되돌리는 동작**(보상)을 한다.

**유래.** "먼저 기록"은 DB 의 **write-ahead logging** — Jim Gray, "Notes on Data Base Operating Systems"(1978), ARIES(Mohan 외, 1992). **보상 트랜잭션**은 **Garcia-Molina·Salem, "Sagas"(1987)** — 긴 트랜잭션을 보상 가능한 짧은 단계로 쪼갠 것. **Transactional Outbox** 라는 이름은 Chris Richardson(microservices.io, 『Microservices Patterns』 2018).

**우리가 풀려던 문제.** 최악의 상태는 "콜백은 나갔는데 우리 기록이 없다" — 재전송도 감사도 못 한다. 그래서 RESULT_READY 와 콜백 본문을 **먼저 저장**하고 그 뒤에 보낸다. 프로필 upsert 가 실패하면 실행을 FAILED 로 되돌린다 — 콜백은 나갔는데 Chat 이 읽을 프로필이 없는 상태를 막으려고([03 §13](03_디자인_패턴.md)).

**없애면.** 저장 실패가 콜백 뒤에 드러나면 Backend 는 결과를 받았는데 우리는 그 사실을 모른다. 같은 번호 재요청이 오면 재분석해 **다른 결과**를 보낼 수 있다.

**판정 — 필수.** 비용은 왕복 두 번(RESULT_READY 저장 + DELIVERED 저장) — [06 §3](06_병목과_성능.md)의 그림에서 ⑥과 ⑧이 그것이다. **과해지는 신호:** 별도 아웃박스 표 + 릴레이 프로세스. Backend 의 재요청이 복구 경로를 대신하므로 v1 에서는 불필요하고, 위키가 DB 큐를 금지했다.

## 14. TTL 캐시 · 이중 검사 잠금 · 스냅샷 교체

세 패턴이 한 클래스(`DbCatalogReader`)에 겹쳐 있어 **따로 판정**한다.

**정의.** **TTL 캐시**: 만료 시간이 있는 캐시. **이중 검사 잠금**(double-checked locking): 락 밖에서 한 번 검사하고, 통과했을 때만 락을 잡은 뒤 **다시** 검사해 불필요한 락 획득을 피한다. **스냅샷 교체**: 새 값을 다 만든 뒤 참조 하나를 바꿔, 읽는 쪽이 반쯤 바뀐 것을 못 보게 한다.

**유래.** TTL — DNS 의 캐시 만료(**Mockapetris, RFC 1034/1035, 1987**). 이중 검사 잠금 — **Douglas Schmidt·Tim Harrison, PLoP 1996**, C++ 싱글턴 초기화 최적화. Java 에서는 메모리 모델 때문에 **깨진 패턴**으로 유명해졌다("The Double-Checked Locking is Broken Declaration", Bacon 외, 2001) — JDK 5 의 `volatile` 로 고쳐졌다. 파이썬은 GIL 덕에 참조 교체가 원자적이라 그 함정이 없다. 스냅샷 교체 — copy-on-write 계열, 리눅스의 RCU(McKenney·Slingwine, 1998).

**우리가 풀려던 문제.** ① 7.6 한 건이 접수와 슬롯에서 활성 버전을 두 번 폴링해 왕복 8 — TTL 1초로 0~2([06 §3](06_병목과_성능.md), 그림 ①·⑤). ② 폴링과 적재 사이에 카탈로그가 교체되면 "버전은 옛것, 상품은 새것"이 될 수 있어 `(버전, 상품)` 튜플을 한 번에 바꾼다. ③ 버전이 바뀐 것을 여러 워커가 동시에 보면 4,231건 적재(40ms)를 여러 번 하지 않게 락([03 §14](03_디자인_패턴.md)).

**없애면.** TTL 을 빼면 왕복 8 이 돌아온다(측정값). 튜플 교체를 빼면 불일치 순간이 생긴다(드물지만 콜백에 존재하지 않는 상품 번호가 섞일 수 있다). 이중 검사를 빼고 그냥 `with self._lock:` 으로 감싸면 — **정확성은 같고**, 버전이 안 바뀐 폴링(대부분)에도 락을 잡는다. 워커 4개에서 그 비용은 마이크로초다.

**판정 — TTL 필수 · 스냅샷 교체 필수 · 이중 검사는 선택.** 이중 검사가 남아 있는 이유는 성능이 아니라 "락 안에서 하는 일은 적재뿐"이라는 **설명력**이다. 사용자가 "코드 세 줄과 설명 부담을 덜겠다"고 하면 단순 락으로 바꿔도 잃는 게 없다. **과해지는 신호:** 캐시가 둘 이상 생기고 각자 TTL 을 가질 때 — 그땐 캐시 층을 따로 뽑는다.

## 15. 설정 객체 (12-factor)

**정의.** 환경마다 다른 값은 코드가 아니라 **환경변수**에서 오고, 코드는 그것을 **한 객체**로 읽어 검증·기본값·설명을 한 곳에 둔다.

**유래.** **"The Twelve-Factor App"(Adam Wiggins, Heroku, 2011)** 의 III. Config — "설정을 환경에 저장하라". 배포 환경(dev/staging/prod)마다 코드가 달라지는 것을 막으려는 PaaS 쪽 동기였다. 파이썬에서는 pydantic 의 `BaseSettings`(2019~; 2023 에 `pydantic-settings` 로 분리).

**우리가 풀려던 문제.** 로컬·compose·스테이징의 주소·토큰·슬롯·큐 값이 다르고, alembic 과 앱이 **같은** `DATABASE_URL` 을 봐야 한다. `Field(description=…)` 이 곧 설정 문서다([09 §1](09_운영과_도구.md)). 대가도 치렀다: 접두사 처리의 날카로운 모서리 때문에 `PROFILING_SLOTS` 가 안 읽히고 `PROFILING_PROFILING_SLOTS` 라야 먹었다([이슈 2026-09-28_1424](../issues/2026-09-28_1424_slots-env-name/README.md)) — 편의 기능은 공짜가 아니다.

**없애면.** `os.environ["X"]` 가 흩어지고 기본값·검증이 각자 논다.

**판정 — 적정.** 여기도 **판단 지점**이 하나 있다: 설정 19개 중 환경마다 **실제로 다른** 것은 6개쯤(DB 주소·Backend 주소·토큰·카탈로그 소스·슬롯·큐 상한)이고 나머지는 튜닝 노브(TTL·백오프·드레인 시간…)다. 노브가 많으면 "무엇을 바꿔야 하나"가 흐려진다. 내 의견은 "노브도 문서화돼 있으니 두되, 아무도 안 바꾼 지 한 달이면 상수로 되돌린다". **과해지는 신호:** 설정이 40개를 넘고 설명 없는 항목이 생길 때.

## 16. 오류 봉투 한 곳

**정의.** 모든 오류 응답을 하나의 형식(봉투)으로 내고, 예외 → 봉투 변환은 **한 함수**만 한다.

**유래.** 중앙 예외 처리는 오래된 관행이고, HTTP 에서의 표준화는 **RFC 7807 "Problem Details for HTTP APIs"(Nottingham·Wilde, 2016)** → **RFC 9457(2023)**. 우리는 RFC 형식이 아니라 팀 위키의 봉투 `{message, error:{code, traceId}}`(문서 1)를 따른다 — 형식이 무엇이든 "한 곳에서"가 패턴의 핵심이다. FastAPI 의 `@app.exception_handler` 가 그 자리다.

**우리가 풀려던 문제.** 400·401·422·503 이 전부 같은 봉투여야 Backend 의 파서가 하나다. `Retry-After` 도 한 곳에서 붙는다. 처리기 셋(`HTTPException`·검증 오류·나머지 예외)이 한 함수를 지난다([04 §5](04_통신.md), [03 §16](03_디자인_패턴.md)).

**없애면.** 라우터마다 `JSONResponse` 를 조립하다 한 곳이 봉투가 아니게 되고, Backend 쪽에서 `error.code` 가 없다며 터진다 — 연동 초기의 전형적 사고다.

**판정 — 필수.** 40줄. **과해지는 신호:** 없다.

## 17. 함수형 핵심 / 명령형 껍질

**정의.** 계산·판단은 **순수 함수**(핵심)로, DB·HTTP·시간 같은 부작용은 그것을 감싸는 **얇은 바깥층**(껍질)에서만. 핵심은 표로 시험하고 껍질은 가짜 바깥으로 시험한다.

**유래.** 이름은 **Gary Bernhardt 의 강연 "Boundaries"(2012, SCNA·RubyConf)** — "Functional Core, Imperative Shell". 뿌리는 헥사고날 아키텍처(Cockburn, 2005)와 함수형 전통이고, Mark Seemann 은 같은 모양을 "불순-순수-불순 샌드위치"(2020)라 부른다.

**우리가 풀려던 문제.** 시험 피라미드. 단위 155개가 핵심(`decide`·`build_pool`·`callback_body`·`_lock_key`…)을 겨눠 ms 단위로 돌고, 통합 51개만 진짜 PostgreSQL 을 쓴다([08 §1](08_테스트.md), [03 §17](03_디자인_패턴.md)의 짝 표).

**없애면.** 계산과 I/O 가 섞이면 모든 시험이 통합 시험이 된다. §1·§5·§11 이 무너지는 것과 같은 손해다.

**판정 — 적정.** 비용 0 인 스타일이지만 **한 가지 신호**를 낸다: 순수성을 지키려고 인자가 늘어난다. `profile()` 은 인자 6개, v2 검색 연결 뒤엔 8개가 된다. 인자 8개는 "묶을 때"의 신호다 — 그때는 `Ports` 같은 작은 묶음 객체 하나로 받는 것이 답이지, 순수성을 버리는 것이 답은 아니다.

## 18. 시험 이음매 + 파사드

**정의.** **이음매**(seam): 코드를 고치지 않고 그 자리의 동작을 바꿀 수 있는 지점 — 우리는 `clock=`·`sleep=`·`transport=` 인자. **파사드**(Facade): 서브시스템에 좁고 단순한 문 하나 — 우리는 패키지 `__init__` 의 재수출.

**유래.** 이음매 — **Michael Feathers, 『Working Effectively with Legacy Code』(2004)**: 객체 이음매·링크 이음매·전처리 이음매. 시험 대역의 분류(dummy·stub·spy·mock·fake) — **Gerard Meszaros, 『xUnit Test Patterns』(2007)**. 파사드 — GoF(1994), 구조 패턴.

**우리가 풀려던 문제.** `time.sleep(2)` 이 든 시험은 2초 걸리고, 진짜 네트워크가 든 시험은 가끔 실패한다. 이음매 다섯 개로 콜백 재시도 시험이 0초·결정적이 됐다([03 §18](03_디자인_패턴.md)). 목 라이브러리 대신 Protocol 모양의 가짜를 쓰는 이유는 [08 §3](08_테스트.md).

**없애면.** 이음매를 빼면 재시도 시험 하나가 2.5초, 전체 시험이 수십 초로. `mock.patch("time.sleep")` 으로 대신할 수 있지만 모듈 전역을 바꿔 시험끼리 간섭한다.

**판정 — 이음매 필수 · 파사드 선택(거의 장식).** 파사드는 Q3 에서 걸린다: `from profiling import …` 여덟 곳이 **전부 서브모듈 import**(`from profiling import intake`)이고 재수출 이름(`profile`·`Settings`…)을 쓰는 곳은 **0** 이다. 지워도 아무것도 안 깨진다. 남기는 이유가 있다면 "패키지의 공개 표면이 무엇인지"를 문서처럼 보여 준다는 것뿐이다. **과해지는 신호:** 이음매 인자가 시험만을 위해 프로덕션 서명을 어지럽힐 때 — `clock`·`sleep` 은 기본값이 있어 호출자가 모른 채 지나가므로 아직 아니다.

## 19. 실패 정책 셋

**정의.** **fail-fast**: 그 상태로 도는 것이 더 위험하면 시작하지 않는다. **degrade**(우아한 저하): 핵심은 막되 프로세스는 살려 상태를 보인다. **fail-open**: 보조 장치가 실패하면 없는 셈 치고 진행한다(반대는 fail-closed — 보안에서는 그쪽이 기본).

**유래.** fail-fast — **Jim Gray, "Why Do Computers Stop and What Can Be Done About It?"(1985)**: 모듈은 정확히 동작하거나 즉시 멈춰야 하고, 어중간하게 계속 도는 것이 가장 위험하다. 우아한 저하 — 내결함성 공학(Randell, "System Structure for Software Fault Tolerance", 1975). fail-open/closed — 안전 공학(비상구 잠금, 회로 차단기)에서 온 말. 셋을 서비스 설계 어휘로 묶은 것은 **Nygard, 『Release It!』(2007)**.

**우리가 풀려던 문제.** 실패마다 태도가 달라야 했다. DB 없음 → 죽는다(기록 없는 콜백을 만들지 않으려고). 카탈로그 없음 → 뜨되 7.6 은 503, `/health` 에 이유(사람이 적재하면 재시작 없이 회복). 잠금 못 걺 → 진행(잠금은 중복을 줄이는 장치지 접수를 막는 장치가 아니다). 워커 안 예외 → 그 건만 실패([03 §19](03_디자인_패턴.md)의 표).

**없애면.** 태도를 하나로 통일하면 — 전부 fail-fast 면 카탈로그 적재 전엔 앱을 못 띄우고, 전부 fail-open 이면 DB 없이 콜백이 나간다.

**판정 — 필수.** 이것은 코드가 아니라 **결정**이고, 03 §19 의 표가 그 결정의 문서다. 이 표가 없으면 `try/except` 마다 태도가 다른 이유를 아무도 설명 못 한다. **과해지는 신호:** 없다.

| §15 튜닝 노브 13개 | 상수로 되돌린다 | 설정 표의 길이 | 한 달 안 바꾸면 상수로 |

반대로 **부족한 것**도 하나 적어 둔다. 실패 정책(§19)이 표로만 있고 코드에 이름이 없다 — `try/except` 옆 주석에 "fail-open" 같은 말을 남기면 다음 사람이 표 없이도 읽는다. 패턴을 더 넣는 게 아니라 **이름을 붙이는** 것이라 비용이 0 이다.
