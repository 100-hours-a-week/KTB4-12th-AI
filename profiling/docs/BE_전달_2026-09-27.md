## 1. 7.6 — Backend → AI (추천 요청 접수)

```
POST /api/internal/v1/ai/profile/extract-and-pool
Authorization: Bearer <serviceToken>
Content-Type: application/json
```

### 요청 본문 (v1)

| 필드 | 타입 | 필수 | 값 |
|---|---|---|---|
| `recipientUserId` | integer > 0 | ✔ | 수신자 `users.id` |
| `sourceVersion` | integer ≥ 0 | ✔ | **7.6을 보내기 직전에 +1 하고 커밋한 번호** |
| `dislikedCategories` | array | ✔ | 없으면 `[]` (키 생략 불가) |
| `dislikedCategories[].categoryId` | integer > 0 | ✔ | `categories.id` — **대분류 id 1~10** (BE는 root만 저장, 최대 5). AI가 그 대분류의 **하위 소분류 전체**를 제외합니다(09-27 결정) |
| `dislikedCategories[].categoryName` | string | ✔ | `categories.name` |

```json
{"recipientUserId": 9871, "sourceVersion": 3,
 "dislikedCategories": [{"categoryId": 1, "categoryName": "뷰티"}]}
```

> `giftPreference`·`reviews` 키는 계약에 있지만 **v1에서는 보내지 않아도 됩니다.** 보내도 받습니다(v1은 무시하고 경고 로그만 남깁니다). 계약에 없는 필드가 와도 **400이 아니라 무시 + 경고**입니다 — 필드를 추가해도 연동이 깨지지 않습니다.

### 응답

| 코드 | 언제 | 본문/헤더 | Backend가 할 일 |
|---|---|---|---|
| **202** | 접수됨 | `{message, data:{recipientUserId, sourceVersion, profileStatus:"PENDING"}}` | §3 ②의 조건부 PENDING 처리 |
| 400 `INVALID_REQUEST` | 본문이 계약과 다름 | 어디가 틀렸는지 `message`에 | 고쳐서 재요청 (상태 불변) |
| 401 `UNAUTHORIZED` | 토큰 없음·불일치 | | 토큰 확인 (상태 불변) |
| 503 `SERVICE_UNAVAILABLE` | AI에 활성 카탈로그 없음 | **헤더 `Retry-After: 300`** | 그 초 뒤 **같은 번호**로 재시도 (상태 불변) |
| 500 `INTERNAL_SERVER_ERROR` | AI 내부 오류 | | 백오프 뒤 **같은 번호**로 재시도 (상태 불변) |

오류 봉투는 전부 같은 모양입니다: `{"message": "...", "error": {"code": "...", "traceId": null}}`

**토큰과 본문이 둘 다 틀리면 401이 먼저** 옵니다(FastAPI가 의존성을 본문보다 먼저 풉니다 — 실제로 확인했습니다).

## 2. 7.7 — AI → Backend (추천 결과 콜백)

```
POST {BE}/api/internal/v1/recipients/{recipientUserId}/profile
Authorization: Bearer <serviceToken>
```

| 필드 | 타입 | 값 |
|---|---|---|
| `recipientUserId` | integer | 경로의 값과 같아야 합니다 |
| `sourceVersion` | integer | **7.6에서 받은 값 그대로** — AI는 절대 바꾸지 않습니다 |
| `profileStatus` | string | 항상 `"COMPLETED"` |
| `recommendedProductIds` | integer[] ≤ 30 | `products.id`. **순서가 곧 순위**입니다 |

```json
{"recipientUserId": 9871, "sourceVersion": 3, "profileStatus": "COMPLETED",
 "recommendedProductIds": [3769, 2464, 1459, "…27개 더"]}
```

**태그는 보내지 않습니다**(09-16 합의 DR-035). 태그는 AI가 자기 표에 보관하고, Backend에는 상품 번호만 갑니다.

### Backend 응답에 따른 AI 동작

| Backend 응답 | AI가 하는 일 | AI 실행 기록 |
|---|---|---|
| **200** | 끝 | `DELIVERED` |
| **409** `STALE_SOURCE_VERSION` | 폐기(정상 경로) | `SUPERSEDED` |
| 400 · 401 · 403 | 재시도 없음 — 계약이 안 맞는다는 뜻이라 로그로 남깁니다 | `FAILED` |
| 5xx · 타임아웃 · 연결 실패 | **즉시 3회**(0.5초·2초 뒤) 다시 보내고, 그래도 안 되면 결과를 보관합니다 — 같은 번호로 다시 요청하시면 재분석 없이 재전송 | `RESULT_READY` (미전달) |

> 마지막 줄이 중요합니다. **AI는 5xx를 스스로 재시도하지 않습니다.** 그 결과는 "결과는 있는데 못 보낸" 상태로 남고, **Backend가 같은 번호로 다시 요청할 때 재전송**됩니다(§4). 그 행의 개수는 `GET /health`의 `store.undelivered`로 볼 수 있습니다.

## 3. `profileStatus` 생애주기 — Backend가 저장·판정

AI는 값을 보내기만 하고, **저장과 판정은 Backend**입니다. **AI는 `FAILED`를 보내지 않습니다**(실패하면 침묵). 

### Backend가 수신자마다 들고 있어야 하는 값

| 열 | 뜻 | 바뀌는 때 |
|---|---|---|
| `profile_status` | `NONE` · `PENDING` · `COMPLETED` · `FAILED` | 아래 세 군데 |
| `source_version` | 마지막으로 **보낸** 7.6 번호 | 7.6 보내기 직전 +1 **하고 커밋** |
| `analyzed_source_version` | 저장된 7.7 결과의 번호 | 7.7 저장 때 |
| `recommended_product_ids` | 7.7의 30개 | 7.7 저장 때 |
| `last_changed_at` | 마지막 변경 시각(디바운스 기준) | 사용자가 비선호 수정 때 · 202 때 **조건부로** 비움 |
| `window_started_at` | 최초 미반영 변경 시각(상한 기준) | 첫 변경 때 · 202 때 비움 |
| `pending_since` | PENDING이 된 시각(타임아웃 판정) | 202 때 |
| `retry_count` | **재전송** 횟수 (최대 2) | 재전송 때 +1 · 새 번호 요청이나 7.7 저장 성공 때 0 |

### 상태가 바뀌는 곳은 **세 군데뿐**

```
202 → PENDING       (조건부, 아래 ②)
7.7 200 → COMPLETED (번호가 최신일 때)
타임아웃 → FAILED    (재전송 2회를 다 쓴 뒤)
```

**오류 응답(400·401·503·500)은 상태를 바꾸지 않습니다.**

### ① 7.6을 보낼 때

```
if last_changed_at 있음 and (now - last_changed_at ≥ 디바운스 or now - window_started_at ≥ 상한):
    source_version += 1 ; 커밋          # ← 요청보다 먼저. 번호는 "보낸 순번"
    보내기 직전의 last_changed_at 값을 기억
    POST 7.6 (sourceVersion = source_version)     # ← 트랜잭션 밖에서 (§6)
```

### ② 202를 받았을 때 — 조건 두 개가 핵심입니다

```
if analyzed_source_version < sourceVersion:      # 이 번호의 결과가 아직 없을 때만
    profile_status = PENDING ; pending_since = now()
if last_changed_at == 보내기 직전에 읽은 값:       # 그 사이 수정이 없었을 때만
    last_changed_at = NULL ; window_started_at = NULL
```

첫 조건이 없으면 **7.7이 202보다 먼저 처리될 때**(v1은 콜백까지 50ms) `COMPLETED`를 `PENDING`으로 덮고 타임아웃 뒤 `FAILED`로 오판합니다. 둘째 조건이 없으면 분석 중에 들어온 수정이 대기열에서 사라집니다.

### ③ 7.7을 받았을 때

```
if body.recipientUserId != path.recipientUserId: 400 RECIPIENT_ID_MISMATCH
if body.sourceVersion < analyzed_source_version: 409 STALE_SOURCE_VERSION   # 낡은 결과가 최신을 덮는 것만 거부
else:
    recommended_product_ids = body.recommendedProductIds
    analyzed_source_version = body.sourceVersion
    retry_count = 0
    if body.sourceVersion == source_version: profile_status = COMPLETED ; pending_since = NULL
    # 더 낮은 번호면 새 요청이 진행 중 — 30개는 갱신하되 PENDING 유지
    200
```

**같은 번호가 다시 와도 그대로 저장하고 200**을 주세요(재전송이므로). 멱등해야 합니다.

### ④ PENDING 타임아웃

```
if profile_status == PENDING and now - pending_since ≥ 타임아웃 and last_changed_at is NULL:
    if retry_count < 2: retry_count += 1 ; 같은 번호로 7.6 재전송      # §4
    else:               profile_status = FAILED
```

`last_changed_at`이 있으면(대기 중인 수정이 있으면) FAILED로 바꾸지 마세요 — 어차피 다음 7.6이 나갑니다.

## 4. 재시도 — 같은 번호로, 최대 2회 (BE 계획 5-1·5-2 와 같은 모델)

새 요청만 **새 번호**이고, 그 번호가 실패하면 **같은 번호로** 다시 보냅니다. 접수 실패(7.6이 500·503·연결 실패·타임아웃)든 결과 미도달(202는 받았는데 7.7이 안 옴)이든 **`retry_count` 하나로 셉니다**(최대 2). AI 쪽 말로는, 같은 번호가 다시 왔을 때 저장된 결과를 다시 보내는 것을 **재전송**이라고 부릅니다.

| BE가 본 것 | BE 동작 (BE 계획 5-1) | AI가 가진 것 |
|---|---|---|
| 7.6 → 400 `INVALID_REQUEST` · 401 `UNAUTHORIZED` | 재시도 없음 — 계약·토큰 문제, 고친 뒤 새 번호 | 없음(접수 안 됨) |
| 7.6 → 500 · 연결 실패 · 응답 타임아웃 | 백오프 뒤 **같은 번호** 재시도 (`retry_count` +1) | 없음 — 같은 번호가 오면 그때 분석 |
| 7.6 → 503 `SERVICE_UNAVAILABLE` | **`Retry-After`(300초) 뒤** 같은 번호 재시도 | 없음 |
| 202 받았는데 7.7이 10분 안에 안 옴 | PENDING 타임아웃 → 같은 번호 재시도 (`retry_count` +1) | 결과가 있으면 **재분석 없이 재전송**, 없으면 분석 |
| `retry_count` 2를 다 쓰고도 실패 | `FAILED` — 사용자가 다시 고칠 때 새 번호 | AI는 그 뒤에도 아무것도 보내지 않음 |

`retry_count`는 **새 번호를 보낼 때와 7.7 결과를 저장했을 때 0**이 됩니다. 재시도를 기다리는 동안 사용자가 또 고치면 옛 번호 재시도는 버리고 **새 번호**가 나갑니다(낡은 입력으로 재시도하지 않기 위해).

### 같은 번호를 받으면 AI가 하는 일

| AI 쪽 상태 | 하는 일 |
|---|---|
| 분석 중(`RUNNING`) | **아무것도 안 함** — 분석이 두 벌 돌지 않게. 원래 실행이 끝나면 콜백이 갑니다 |
| 결과 있음(`RESULT_READY`·`DELIVERED`·`SUPERSEDED`) | **재분석 없이 7.7 재전송** — 최초와 **완전히 같은 30개** |
| 실패(`FAILED`) · 죽은 `RUNNING`(5분 초과) | 다시 분석 |
| 같은 번호인데 **본문이 다름** | 다시 분석 — 그래서 **재전송 본문은 최초와 같아야 합니다** |

어느 경우든 응답은 `202 PENDING`입니다.

**왜 같은 번호여야 하나**: AI의 실행 기록은 `(수신자, sourceVersion)` 한 행입니다. 같은 번호면 그 행에 모이고 저장된 결과를 그대로 다시 보낼 수 있습니다. 새 번호로 보내면 매번 전체 재분석이라, 그 사이 카탈로그가 바뀌면 같은 요청인데 추천이 달라집니다.

### 다중 인스턴스라면

`retry_count` 증가를 **조건부 원자 갱신**으로 해주세요. 스케줄러 두 대가 같은 타임아웃을 보면 2회가 한꺼번에 나갑니다.

```sql
UPDATE profiles SET retry_count = retry_count + 1
 WHERE recipient_user_id = ? AND retry_count < 2
```

## 6. ⚠ 트랜잭션 — 꼭 지켜 주세요

**① 7.6 호출을 트랜잭션 안에서 하지 마세요.**

`source_version += 1`을 **커밋한 뒤** 호출해야 합니다. 트랜잭션을 연 채 호출하면, AI 콜백(7.7)이 **50ms 만에** 도착해서 아직 커밋되지 않은 행을 읽거나 잠금 대기에 걸립니다.

```
✗  BEGIN → version+1 → POST 7.6 → (그 사이 7.7 도착) → COMMIT
✓  BEGIN → version+1 → COMMIT → POST 7.6
```

**② 7.7 수신은 짧은 트랜잭션 하나로, 멱등하게.** 번호 비교 → 저장 → 상태 전이를 한 트랜잭션에서 끝내고, 같은 번호를 다시 저장해도 결과가 같아야 합니다.

**③ AI는 Backend 트랜잭션에 참여하지 않습니다.** 분산 트랜잭션이 없으니, AI가 실패해도 Backend 데이터에는 영향이 없습니다(그 반대도 마찬가지).

참고로 AI 쪽은 같은 성격의 문제 두 개를 09-26·27에 닫았습니다 — 같은 `(수신자, 번호)` 동시 접수 시 분석이 두 벌 돌던 것(DB advisory lock), 카탈로그 버전과 상품을 따로 읽어 어긋날 수 있던 것(한 문장 조인). 그 잠금은 **세션 단위이고 트랜잭션을 열어두지 않습니다**(얻은 직후 커밋) — 그래서 긴 작업에서도 세션 타임아웃에 끊기지 않고, 판정부터 콜백까지 한 잠금 안에 있다는 말이 v3에서도 성립합니다.

## 8. 연동 시작 절차

1. Backend 주소·서비스 토큰 교환 (§7 6번)
2. AI 쪽 `.env`에 주입 → `GET /health`로 확인 (`catalog.active: true` · `products: 4231`)
3. Backend에서 7.6 한 건 발사 → AI 로그에 `7.6 접수` → `7.7 콜백 … 200 DELIVERED`
4. Backend `profiles` 행 확인 — `analyzed_source_version == source_version` · `profile_status = COMPLETED` · 30개 저장
5. 같은 번호로 한 번 더 발사 → AI 로그에 `재전송 … 재분석 없음`, Backend는 같은 30개를 다시 저장

막히면 AI `GET /health`를 먼저 봐주세요 — 카탈로그 활성 여부·DB 연결·마이그레이션 버전·미전달 결과 수·슬롯 상태가 한 번에 나옵니다.

```json
{"status":"ok",
 "catalog":{"active":true,"version":"44375124-…","products":4231},
 "store":{"backend":"db","connected":true,"migration":"0003","undelivered":0},
 "supervisor":{"slots":1,"running":0,"submitted":0}}
```
