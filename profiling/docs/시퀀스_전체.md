# 프로파일링 전체 시퀀스 (2026-09-23 구현 기준)

지금 `profiling/src/profiling/` 에 **실제로 들어 있는 코드**가 요청 한 건을 어떤 순서로 처리하는지 그린 문서. 계약(무엇을 주고받는가)은 [BE_연동_필드표](BE_연동_필드표.md)에 있고, 이 문서는 **우리 쪽 내부 순서**(어느 파일의 어느 함수가 언제 불리는가)를 본다. 구조 그림은 [README §1](../README.md), 다음 할 일은 [파이프라인 지도](파이프라인_지도/)에 있다.

| 절 | 내용 |
|---|---|
| 1 | 등장 요소 — 파일과 역할 |
| 2 | 기동 — 조립(lifespan) |
| 3 | **성공 전체** — 접수(동기 202) + 분석(백그라운드) + 콜백 |
| 4 | 접수 단계에서 끝나는 경우 — 401 · 400 · 503 · 500 |

## 1. 등장 요소

| 그림 이름 | 파일 | 하는 일 |
|---|---|---|
| `APP` | [main.py](../src/profiling/main.py) | 조립(lifespan) · 오류 봉투 핸들러 · `/health` |
| `R` | [intake.py](../src/profiling/intake.py) | 7.6 라우터(`extract_and_pool`)와 백그라운드 작업(`run_and_callback`) |
| `SUP` | [supervisor.py](../src/profiling/supervisor.py) | 실행 슬롯(세마포어) |
| `PL` | [pipeline.py](../src/profiling/pipeline.py) | 업무 순서 — 변환·판단·풀 만들기 (바깥을 모름) |
| `CAT` | [catalog.py](../src/profiling/catalog.py) | 활성 카탈로그 (오늘은 파일, 다음은 `ai_catalog` DB) |
| `ST` | [stores.py](../src/profiling/stores.py) | `profile_runs`(실행 기록) · `recipient_profiles`(수신자 프로필) |
| `BP` | [backend.py](../src/profiling/backend.py) | 7.7 콜백 송신 (HTTP 상태 → `RunStatus` 번역) |

`PL`은 `CAT`·`ST`를 **import하지 않는다** — [ports.py](../src/profiling/ports.py)의 모양(Protocol)으로 인자를 받는다. 그래서 그림의 `PL → CAT`·`PL → ST` 화살표는 전부 "main.py가 끼워 넣은 구현"으로 간다.

## 3. 성공 전체

![성공 전체](assets/seq/01-성공-전체.png)

<!-- fig: 01-성공-전체 -->
```mermaid
sequenceDiagram
  autonumber
  participant BE as Backend
  participant APP as main.py
  participant R as intake.py
  participant SUP as supervisor.py
  participant PL as pipeline.py
  participant CAT as catalog.py
  participant ST as stores.py
  participant BP as backend.py
  participant DB as PostgreSQL

  BE->>APP: POST 7.6 extract-and-pool (Bearer, sourceVersion v)
  APP->>R: require_service_token — 토큰 검사가 본문 검증보다 먼저
  APP->>APP: ProfileExtractRequest 검증 (pydantic)
  APP->>R: extract_and_pool(body, bg, ...)
  R->>CAT: active()
  CAT-->>R: (catalog_version_id, products)
  R->>R: unknown_fields(body) — 계약에 없는 필드는 경고만 남기고 진행
  R->>R: pipeline.to_internal(body) → ProfileRequest (camelCase → snake_case)
  R->>SUP: submit(bg, run_and_callback, rq, ...)
  R-->>BE: 202 {profileStatus: PENDING, sourceVersion: v}

  Note over BE,DB: 여기까지가 동기 구간. 아래는 응답을 보낸 뒤 BackgroundTasks 스레드에서 돈다

  SUP->>SUP: 세마포어 슬롯 확보 (차 있으면 대기)
  SUP->>R: run_and_callback(rq, ...)
  R->>PL: profile(rq, catalog=, store=, recipient_store=, pool_size=30)
  PL->>ST: save(RUNNING, input_hash)
  ST->>DB: upsert profile_runs — attempt +1
  PL->>CAT: active() — 한 요청은 끝까지 같은 버전을 쓴다
  CAT-->>PL: (catalog_version_id, products)
  PL->>PL: needs_model() — v1은 취향·리뷰가 없어 모델 단계를 건너뛴다
  PL->>PL: ValidationResult(disliked_tags = 비선호 카테고리 이름)
  PL->>PL: build_pool() — 비선호 제외 · available · 조회수 내림차순 30개
  PL->>ST: save(RESULT_READY + callback_payload)
  ST->>DB: upsert profile_runs — 콜백 본문이 먼저 커밋된다
  PL->>ST: upsert(RecipientProfile)
  ST->>DB: upsert recipient_profiles — 낮은 버전이 늦게 오면 DB가 무시
  PL-->>R: ProfileOutcome(RESULT_READY)
  R->>BP: send_profile_callback(outcome)
  BP->>BP: to_callback() — RESULT_READY만 허용 · 태그 없음 · ids ≤ 30
  BP->>BE: POST 7.7 {recipientUserId, sourceVersion: v, COMPLETED, recommendedProductIds}
  BE-->>BP: 200
  BP-->>R: CallbackResult(DELIVERED)
  R->>ST: save(status=DELIVERED, callback_attempts +1)
  ST->>DB: upsert profile_runs
```

읽는 요령 셋.

1. **202는 카탈로그 확인까지만 보고 나간다.** 활성 카탈로그가 없다는 사실을 백그라운드에서 알게 되면 Backend는 영영 모르기 때문에, 그 검사만 접수 단계로 끌어올렸다.
2. **DB 쓰기가 콜백보다 먼저다.** `RESULT_READY + 콜백 본문`을 커밋한 다음에 7.7을 보낸다. 그래야 "보냈는데 우리 쪽에 기록이 없는" 상태가 생기지 않는다.
3. **같은 행을 세 번 쓴다.** `RUNNING → RESULT_READY → (콜백 결과)`. 키는 `(recipient_user_id, source_version)`이고, `RUNNING`으로 다시 들어올 때만 `attempt`가 올라간다.

## 4. 접수 단계에서 끝나는 경우

![접수 거절](assets/seq/02-접수-거절.png)

<!-- fig: 02-접수-거절 -->
```mermaid
sequenceDiagram
  autonumber
  participant BE as Backend
  participant APP as main.py
  participant R as intake.py
  participant CAT as catalog.py

  alt 토큰 없음 · Bearer 아님 · 값 불일치
    BE->>APP: POST 7.6
    APP->>R: require_service_token
    R-->>APP: HTTPException(401, UNAUTHORIZED)
    APP-->>BE: 401 {message, error: {code: UNAUTHORIZED, traceId: null}}
  else 본문이 계약과 다름 (JSON 아님 · 필수 필드 없음 · 타입 위반)
    BE->>APP: POST 7.6
    APP->>APP: RequestValidationError (FastAPI 기본 422)
    APP-->>BE: 400 {code: INVALID_REQUEST, message: "요청 형식이 올바르지 않습니다: 위치 — 사유"}
  else 활성 카탈로그 없음
    BE->>APP: POST 7.6
    APP->>R: extract_and_pool
    R->>CAT: active()
    CAT-->>R: NoActiveCatalog
    R-->>APP: HTTPException(503, SERVICE_UNAVAILABLE)
    APP-->>BE: 503 {code: SERVICE_UNAVAILABLE, message: "활성 카탈로그가 없습니다."}
  else 그 밖의 예외
    BE->>APP: POST 7.6
    APP-->>BE: 500 {code: INTERNAL_SERVER_ERROR}
  end
  Note over BE: 네 경우 모두 백그라운드 작업이 시작되지 않는다 — profile_runs 행도 없고 7.7도 없다
```

- **토큰과 본문이 둘 다 틀리면 401이 나온다.** FastAPI가 의존성을 본문보다 먼저 풀기 때문이고, 최소 앱으로 확인했다.
- 오류 응답은 전부 `main._error_response()` 하나를 지난다 — 봉투 모양이 어긋날 곳이 한 군데뿐이다.
- 403 FORBIDDEN은 지금 나오지 않는다(서비스 토큰이 하나뿐).

## 5. 분석 단계 실패 — 침묵

202를 이미 보낸 뒤라 Backend에 알릴 방법이 없다. **AI는 FAILED를 콜백하지 않는다.** Backend는 콜백이 오지 않으면 다음 디바운스 주기에 7.6을 다시 보낸다.

![분석 실패](assets/seq/03-분석-실패.png)

<!-- fig: 03-분석-실패 -->
```mermaid
sequenceDiagram
  autonumber
  participant R as intake.run_and_callback
  participant PL as pipeline.profile
  participant ST as stores.py
  participant DB as PostgreSQL
  participant BE as Backend

  R->>PL: profile(rq, ...)
  alt 0) RUNNING 저장 실패 (DB 끊김)
    PL->>ST: save(RUNNING)
    ST-->>PL: 예외
    PL-->>R: FAILED / STORE_FAILED — 기록도 남기지 못한다
  else 1) 활성 카탈로그 없음 (접수 뒤에 사라짐)
    PL-->>R: FAILED / NO_ACTIVE_CATALOG (기록 저장)
  else 2~4) 업무 단계 예외
    PL-->>R: FAILED / PIPELINE_ERROR (기록 저장)
  else 5) 결과 저장 실패
    PL-->>R: FAILED / STORE_FAILED
  else 6) 수신자 프로필 저장 실패
    PL->>ST: upsert(RecipientProfile)
    ST-->>PL: 예외
    PL-->>R: FAILED / STORE_FAILED — 여기서 RESULT_READY로 돌려주면 Chat이 읽을 프로필 없이 콜백만 나간다
  end
  R->>R: status != RESULT_READY → 경고 로그만
  Note over R,BE: 7.7 콜백 없음. Backend는 다음 주기에 같은 sourceVersion으로 다시 7.6
  Note over PL,DB: profile() 자체가 예외를 밖으로 내지 않는다. 그래도 run_and_callback이 try로 한 번 더 감싼다 — 백그라운드에서 죽으면 조용히 사라지기 때문
```

## 6. 콜백 결과 네 갈래

`backend._status_from_response()`가 HTTP 상태를 **실행 기록의 다음 상태**로 번역한다. 새 타입을 만들지 않고 `RunStatus` 하나로 돌려준다.

| 7.7 응답 | 다음 상태 | 오류 코드 | 뜻 |
|---|---|---|---|
| 200 | `DELIVERED` | — | 전달 완료 |
| 409 | `SUPERSEDED` | `CALLBACK_STALE` | 더 새 버전이 이미 저장됨 → 결과 폐기, 재시도 없음 (정상 경로) |
| 400 · 401 · 403 | `FAILED` | `CONTRACT_7_7_REJECTED` | 우리 쪽 버그나 토큰 → 재시도 없음 |
| 5xx · 타임아웃 · 연결 실패 | `RESULT_READY` | `CALLBACK_UNREACHABLE` | 아직 전달 못 함 → **재시도 대상**(오늘은 1회만 보내고 멈춘다) |

![콜백 결과](assets/seq/04-콜백-결과.png)

<!-- fig: 04-콜백-결과 -->
```mermaid
sequenceDiagram
  autonumber
  participant R as intake.run_and_callback
  participant BP as backend.py
  participant BE as Backend
  participant ST as stores.py

  R->>BP: send_profile_callback(outcome)
  BP->>BE: POST 7.7
  alt 200
    BE-->>BP: 200
    BP-->>R: DELIVERED
  else 409 STALE_SOURCE_VERSION
    BE-->>BP: 409
    BP-->>R: SUPERSEDED / CALLBACK_STALE
  else 400 · 401 · 403
    BE-->>BP: 4xx
    BP-->>R: FAILED / CONTRACT_7_7_REJECTED
  else 5xx · 타임아웃 · 연결 실패
    BE--)BP: 5xx 또는 httpx.RequestError
    BP-->>R: RESULT_READY / CALLBACK_UNREACHABLE
  end
  R->>ST: save(status = 위 결과, callback_attempts +1, failure_code, failure_reason)
  Note over ST: RESULT_READY 로 남은 행이 "결과 있음 · 미전달" = 재전송 대상. 재시도·백오프 자체는 아직 없다
```

콜백 본문을 만들지 못하는 경우(`search`가 없음)도 한 갈래 더 있다 — `FAILED / PIPELINE_ERROR`로 돌려주고 HTTP는 나가지 않는다.

## 7. 동시 요청과 슬롯

`PROFILING_SLOTS`(기본 1)만큼만 동시에 분석한다. **접수는 막지 않는다** — 202는 바로 나가고, 분석만 줄을 선다. 거절하지 않는 이유는 Backend가 재시도하게 만드는 것보다 늦게라도 처리하는 편이 v1에 맞아서다.

![슬롯](assets/seq/05-슬롯.png)

<!-- fig: 05-슬롯 -->
```mermaid
sequenceDiagram
  autonumber
  participant BE as Backend
  participant R as intake.py
  participant SUP as supervisor.py
  participant PL as pipeline.py

  BE->>R: POST 7.6 (수신자 A)
  R->>SUP: submit(A)
  R-->>BE: 202
  BE->>R: POST 7.6 (수신자 B) — A가 끝나기 전
  R->>SUP: submit(B)
  R-->>BE: 202
  SUP->>PL: A 실행 (슬롯 1/1)
  Note over SUP: B는 세마포어에서 대기 — 거절하지 않는다
  PL-->>SUP: A 완료
  SUP->>PL: B 실행
  Note over SUP: stats() 가 {slots, running, submitted} 를 /health 로 보여준다
```

같은 수신자에게 두 요청이 연달아 오면 지금은 **둘 다 돌린다**. 뒤엣것이 `profile_runs`의 같은 행을 덮고 `attempt`가 올라간다. "RUNNING이면 새 분석 없음 · 결과가 있으면 재전송만"은 접수 단계에서 `store.get()`으로 판정해야 하는 다음 작업이다(8절).

## 8. 이 그림에 아직 없는 것

| 없는 것 | 지금 동작 | 들어갈 자리 |
|---|---|---|
| 접수 단계 중복 판정 | 같은 (수신자, 버전)도 다시 돌린다 | `intake.extract_and_pool` — `catalog.active()` 다음에 `store.get()` |
| 7.7 재시도 3회 + 재시작 복구 | 1회 보내고 멈춘다(`RESULT_READY`로 남음) | `intake.run_and_callback` · 기동 시 미전달 행 스캔 |
| 기한(timeout) · 취소 | 슬롯만 있다 | `supervisor.py` |
| 모델(LLM) 단계 · 검증기 · 팀원 Search | 취향·리뷰가 와도 경고만 남기고 v1 경로 | `pipeline.profile` 2~3단계 (v3) |
| DB 카탈로그 | 파일(`FileCatalogReader`) | `catalog.py`에 `DbCatalogReader` 추가 → `main.lifespan` 한 줄 교체. `backend_product_id`가 채워진 뒤 |

다음 할 일의 정본은 [파이프라인 지도](파이프라인_지도/)다 — 이 표는 그림과 코드 사이의 차이만 적는다.
